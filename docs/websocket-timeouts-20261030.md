# Таймаут первоначального WebSocket-входа на пробном стенде

Дата: 30.10.2026. Основа: `ddb30afa131b1907d5f93c0867a30902d606f5ad`.
Автор поручил расследовать и исправить таймауты, развернуть через GitHub и получить стабильные E2E на VPS. Локальный Docker и локальные проверки больше не используем; штатный CI остается в GitHub. Новый пароль сервера не устанавливаем.

## Подтвержденная цепочка

В публичном браузере DNS завершился, TCP connect завершился, отправлен TLS ClientHello, но ответ TLS не получен до 15-секундного deadline SDK. Запрос Upgrade еще не отправлялся; ICE остается `new`. Затем SDK завершает вход с `ConnectionErrorReason.Timeout`, WebSocket закрывается с 1006, интерфейс показывает ошибку входа. Зависание AudioContext не подтвердилось.

Контрольные проверки того же Caddy: внутри VPS 256/256 успешных новых TLS-соединений; через SSH-туннель к тому же слушателю 256/256. По обычному публичному пути через VPN — 5 таймаутов из 100; дополнительная серия — 4 из 60, включая TLS1.2 и X25519. Ранее напрямую было 265 успешных health-запросов и 12/12 браузерных входов. Размеры/время выборок различаются, абсолютная частота отказов не установлена.

Проверена гипотеза layer4: используемый `caddy-l4 0.1.1` содержит upstream-баг повторного использования TLS-буфера (mholt/caddy-l4 #481/#483). Но при временном исключении layer4 из слушателя на пустом стенде осталось 7 таймаутов из 100. Исходная конфигурация восстановлена и проверена по JSON. Обновление модуля само по себе не устраняет наблюдаемый сбой, оно не входит в этот фикс.

Таким образом, воспроизведен временный отказ внешнего TLS-пути; конкретный узел внутри VPN/маршрута не локализован. Дефект устойчивости приложения подтвержден отдельно кодом: `RTCEngine.join` повторяет только `ServerUnreachable` при заданном `maxRetries`, но исключает `Timeout`; `LiveKitMediaSession.connect` использует один первоначальный сигналинговый запрос с deadline 15 секунд. Повтор открытия после такого отказа может завершиться успешно, но сейчас требует действия пользователя.

## Выбранное решение, версия 3

Повторять временный timeout join-сигналинга в уже существующем SDK-механизме `RTCEngine.join`. Приложение явно задает три попытки; deadline открытия WebSocket остается прежним (15 секунд), ожидание первого сообщения — прежним (5 секунд). Повтор применяется как при первом входе, так и при полном рестарте соединения, который также вызывает join. Resume сохраняет свой прежний timeout. ICE timeout и внешний DefaultReconnectPolicy не меняются, но внутри полного рестарта теперь до трех join-попыток. Счетчик joinAttempts сбрасывается один раз перед новой серией в restartConnection, после cleanup/abort-проверки и проверки наличия signalOpts, но не при рекурсивном retry. При постоянном отказе пользователь будет ждать ошибки дольше, чем раньше; ограничено количество попыток, а не обещан жесткий суммарный deadline. Пользователь остается на существующем экране подключения/восстановления.

Что уже существует:

- `frontend/src/infrastructure/media-session.ts`, `LiveKitMediaSession.connect`: единственный владелец `Room.connect`, задает `autoSubscribe: false`, после успеха настраивает устройства и включает камеру только по намерению владельца.
- Установленный LiveKit 2.23: `RTCEngine.join` уже считает попытки и умеет повторять `ServerUnreachable`, проверяет AbortSignal перед открытием следующего сигналинга. `SignalClient` закрывает старый транспорт и очищает timeout/abort listener.
- `frontend/patches/livekit-client@2.23.0.patch`: существующий точечный патч реального ESM entry; расширяем его, не вводим второй SDK/обертку повторов.
- `frontend/src/application/round-controller.ts`: первоначальные ошибки приходят через rejected connect promise; Disconnected до успешного входа не запускает цепочку повторных HTTP join. Оставляем это поведение.
- `frontend/tests/infrastructure/*-sdk.test.ts`: регрессии установленного ESM SDK с подменой внешних границ; `Room.engine` предоставляет фактический engine без нового test API.
- Инициализационный скрипт собственной Playwright-страницы может заменить только первый WebSocket на EventTarget, который остается CONNECTING до закрытия SDK, затем пропустить следующие конструкторы в настоящий WebSocket. Отдельный `page.routeWebSocket` без connectToServer автоматически открывает сокет; он годится только для отдельного сценария молчащего сервера после Upgrade. Фальшивые камера/микрофон не захватывают устройства автора.

Альтернатива — цикл вокруг всего `Room.connect` в адаптере — повторял бы и ICE/инициализацию устройств и потребовал бы еще одного механизма отмены. Используем существующий счетчик попыток на более узкой сигналинговой границе. Простое увеличение timeout оставляет однократный отказ и заставляет дольше ждать.

## Приемка и границы

A. Первый сигналинговый запрос зависает до Upgrade либо открывается, но не присылает первый ответ (два разных сценария): следующий открывается без повторного HTTP join и без кнопки пользователя, использует ту же identity/token; клиент входит и получает реальный звук/видео. Микрофон выключен до явного включения владельцем.

B. Все запросы зависают: не более трех попыток, затем существующий экран ошибки и возможность явного повторного входа. Никаких бесконечных запросов или автопубликации микрофона.

C. 401/403/404, серверный leave, отмена входа/выход и потеря владения вкладкой не превращаются в временный timeout: нет автоматического повтора запрещенного/отмененного входа. Закрытый предыдущий транспорт не остается активным. Дублирование identity и отзыв участника сохраняют прежние правила.

D. Успешный вход без отказа — одна попытка. Resume сохраняет прежний 15-секундный deadline, а полный restart получает тот же предел трех join-попыток. Ранее установленный звонок продолжает использовать прежний внешний reconnectPolicy; длительное ожидание ICE не получает новый внешний цикл повторов. Проверить сохранение опций resume и retry при full-restart join, а также существующие native recovery E2E в CI.

E. Проверки выполняются на VPS и в GitHub CI. На публичном стенде запускаем все применимые сценарии без локальных test-only admin/UDP fault injectors; локальные-only сценарии остаются в полном CI и не выдаются за публичную приемку. Публичные проверки повторяем без Playwright retries; результаты с выключенным VPN не подменяют проверку восстановления временного отказа.

Долг: механизм не ремонтирует внешний VPN, не гарантирует доступ при постоянном обрыве и не заменяет проверку из независимых сетей. Суммарное ожидание постоянного отказа увеличивается; к join-попыткам добавляется отдельно существующий ICE timeout после удачного сигналинга и закрытие прежнего транспорта. Конкретные 4 секунды отклонены после ревью: настройка сохранилась бы в resume и обрывала бы ранее допустимые медленные соединения. Upstream-баг layer4 остается отдельным вопросом обновления зависимости.

## План

1. Независимое read-only ревью версии 1 выявило изменение resume/full-restart и неверную границу WebSocket mock. Версия 2 сохраняет существующие deadlines, явно включает retry полного join-рестарта и разделяет pre-upgrade/first-message. Повторное ревью версии 2 нашло общий счетчик на срок жизни engine; версия 3 добавляет сброс на границе каждой серии полного рестарта и регрессию использованного бюджета. Повторное целевое ревью этого пункта.
2. RED на установленном ESM SDK: timeout → новая попытка; предел; отмена; terminal errors; существующий ServerUnreachable; full-restart после успешного первоначального join, использовавшего три попытки, повторный full-restart после исчерпанной серии и сохраненные deadline resume. Подмена — только внешняя сигналинговая граница, настоящая логика engine и классификация ошибок.
3. Минимальный ESM-патч условия retry (Timeout вместе с ServerUnreachable) и сброс счетчика перед новой серией restartConnection; параметр приложения `maxRetries: 3` без websocketTimeout override; обновление hash патча через pnpm. Остальные SDK-патчи сохраняются.
4. Два постоянных E2E: (а) первый WebSocket остается CONNECTING без open, SDK закрывает его и следующая попытка идет в настоящий backend/LiveKit; (б) первый сокет открыт Playwright-маршрутом, но не получает первого сообщения, следующая попытка настоящая. Проверяем число попыток, close старого транспорта, одну identity/HTTP join, muted microphone и работающий RTC. Таймаут ожидания самого сценария учитывает существующие 15 секунд первой попытки; граница подмены описывается явно.
5. На VPS подготовить Node/браузер/зависимости офлайн через Mac, без локального Docker и без обращения VPS к зарубежным серверам; системные библиотеки брать из уже настроенного российского зеркала Ubuntu. Приватные тестовые данные не публиковать.
6. Целевые regression/lint/type checks на VPS; PR → полный зеленый CI → squash main → проверенный GitHub offline artifact → деплой на VPS. На VPS повторить применимые E2E, новый тест временного зависания и проверку 12 участников с 1–3 микрофонами/3–4 камерами. Удалить только собственные тестовые раунды, подтвердить здоровье версии и отсутствие генераторов.

## Реализация и промежуточные проверки на VPS

На исходном ESM SDK новая регрессия дала 4 failed / 8 passed по отсутствию retry. После добавления только timeout retry отдельно воспроизведен старый общий budget полного рестарта: 1 failed / 11 passed, ожидались три вызова, был один. После сброса budget и frozen offline install — 12/12 passed. Компактный patch сохраняет прежние hunks; различие байтов с временной редакцией ESM объяснено только исходными переводами строк, строковое содержимое совпало.

Постоянный pre-upgrade E2E на VPS против старого публичного приложения воспроизвел ошибку подключения; искусственный первый WebSocket оставался CONNECTING до настоящего SDK deadline, реальный следующий еще не создавался. Это не ошибка запуска браузера.

Первый общий frontend-прогон на VPS: 701 passed / 1 failed в существующем StrictMode error-lifecycle тесте. Отдельный повтор прошел. Тест синхронно проверял passive-effect подписку сразу после появления DOM второго mount; ожидание заменено на waitFor той же подписки. Условия одной подписки и полного освобождения при unmount сохранены; продуктовый lifecycle не менялся.

Итоговый полный frontend-набор на VPS: 702/702 (65 файлов), без повторов тестов. После уточнения enum в тестовой factory повторно прошли целевые 12/12, oxlint, TypeScript, dependency-cruiser (83 модуля / 295 зависимостей), Prettier, production build и budget 120,2/150 kB gzip. Приложение на публичном адресе пока остается прежней версией до зеленого GitHub CI и выкладки артефакта. QA-пользователь на VPS ограничен loopback и адресом этого VPS по IPv4/IPv6, чтобы браузеры не обращались к зарубежным STUN/фоновым сервисам.

До успешного прогона исправлены ошибки самой тестовой границы: close CONNECTING моделирует error/1006, а Playwright first-response route не совмещается с подменой конструктора WebSocket.
