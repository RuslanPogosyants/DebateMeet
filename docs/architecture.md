## 1. Глоссарий

Код, идентификаторы и сообщения коммитов — на английском. Словарь связывает русские термины со словами в коде: одно понятие — одно слово в обоих языках.

### Раунд и комнаты

| Термин | В коде | Что значит |
|---|---|---|
| Стартовая страница | — | Общая страница площадки: создать раунд и открыть недавние раунды этого браузера. Списка чужих раундов нет: ссылка — единственный контроль доступа |
| Раунд | `Round` | То, на что ведёт ссылка; id раунда стоит в ссылке и служит ключом доступа. Шесть комнат, чат, таймеры, резолюция, судья, барабан. Создаётся со стартовой страницы (`create_round`). Сброса нет: раунд живёт, пока жива ссылка |
| Комната | `Room` | Одна из шести логических комнат раунда. Все шесть существуют с начала раунда. `room` без префикса в коде — только логическая комната |
| База | `Room.BASE` | Общая комната: сюда входят, здесь зрители |
| Подкомната | `Room.OG`, `Room.OO`, `Room.CG`, `Room.CO`, `Room.JUDGES` | Все комнаты, кроме базы: четыре позиционные и судейская. `recall` работает только для них |
| Позиционная комната | `Room.OG`, `Room.OO`, `Room.CG`, `Room.CO` | Комната подготовки позиции |
| Судейская | `Room.JUDGES` | Комната судьи |
| Медиакомната | `MediaRoom` | Комната LiveKit, одна на раунд, имя — id раунда. Термин только интеграции с LiveKit |
| Сессия | `sid` | Одно подключение участника к медиакомнате. Полное переподключение и вторая вкладка дают новую сессию. У самой медиакомнаты свой id — `room_sid` |

### Люди

| Термин | В коде | Что значит |
|---|---|---|
| Вход | `join` | Вход в раунд по REST: новый участник или повторный вход по id и секрету. Не путать с переходом между комнатами (`enter`) |
| Вход закрыт | `entry_closed` | Новые участники не входят; повторный вход по id и секрету работает. Меняет только администратор |
| Участник | `Participant`, `ParticipantId` | Человек в раунде. Id (12 символов, публичный) и секрет выдаёт сервер при первом входе; браузер хранит их для каждого раунда, имя — одно на все раунды |
| Присутствие | `Presence` | `pending` (вошёл, к медиа ещё не подключился) → `connected` (с `sid`) → `disconnected` с момента T. Кэш состояния LiveKit, сверяется с ним (`sync_presence`). Переходы — раздел 3 |
| Архив участников | `ParticipantRegistry` | Все, кто когда-либо входил в раунд: id, имя, хеш секрета. Отсутствующий дольше 5 минут выселяется из агрегата (выселение, `evict`) и остаётся только здесь; вернувшись, попадает в базу с опущенной рукой |
| Флаг судьи | `JudgeFlag` | Флаг, а не роль. Команды `claim_judge`, `hand_over_judge`, `release_judge`. Когда держатель выходит, флаг сразу свободен и сам не возвращается; вернувшийся берёт его кнопкой «взять снова» |
| Судья | — | Участник, у которого сейчас флаг. Отдельной сущности нет |
| Администратор | `admin` | Автор площадки. Выполняет служебные команды на сервере (раздел 3). Не роль в раунде и не интерфейс |

### Ход раунда

| Термин | В коде | Что значит |
|---|---|---|
| Позиция | `Position`: `OG`, `OO`, `CG`, `CO` | Команда в БПФ. Слово «стол» не используем. В интерфейсе — OG / OO / CG / CO |
| Резолюция | `Motion` | Текст резолюции и необязательный инфослайд (`Infoslide`) |
| Таймер | `Timer` | Серверное состояние: длительность, статус (`stopped`, `running`, `paused`), момент окончания или остаток. Клиент тикает сам. Два таймера: подготовки (показывает остаток) и речи (показывает прошедшее время). Длительность меняет судья (`configure_timer`) |
| Речь | `speech_no` | Номер речи под таймером. «Следующая речь» — `next_speech`, её отмена — `undo_next_speech` |
| Грейс | `grace` | 15 с после конца речи |
| Защищённое время | `protected` | Первая и последняя минута речи; при 7:00 — 0:00–1:00 и 6:00–7:00. Подсвечивается не только цветом |
| Сигнал | `Cue` | Звук в 1:00, за минуту до конца, в конце и в конце грейса; при 7:00 — 1:00, 6:00, 7:00, 7:15. Только клиент |
| Рука | `Hand`: `raise_hand`, `lower_hand` | Поднятая рука. Номер в очереди (`HandQueue`) — порядок подъёма внутри комнаты |
| Барабан | `Drum` | В интерфейсе — «жребий». Включённые позиции и те, что ещё не выпали. Команды `draw`, `reset_drum`, `configure_drum` (какие позиции включены и режим `remove_drawn`) |
| Переход | `enter` | Участник сам уходит в другую комнату |
| Вернуть подкомнату в базу | `recall(room)` | Кнопка судьи на подкомнате: все, кто в ней, уходят в базу |
| Всех в базу | `recall_all` | Кнопка судьи: все из всех подкомнат уходят в базу |
| Выключить микрофон | `mute` | Судья выключает чужой микрофон. Включить может только сам участник, по запросу (`request_unmute`) |

### Чат и события

| Термин | В коде | Что значит |
|---|---|---|
| Чат | `Message`, `SystemMessage` | Поток сообщений раунда; отдельного объекта «чат» нет. Написать — `post_message`. Системные строки — результаты барабана |
| Реакция | `Reaction` | Эфемерная: идёт через бэкенд участникам своей комнаты, без гарантии доставки и вне домена |
| Доменное событие | `DomainEvent` | Факт в прошедшем времени: `HandRaised`, `TimerStarted`, `PositionDrawn`… |
| Журнал | `EventLog` | Все доменные события с серверным временем. Пользователи его не видят |
| Снимок | `RoundSnapshot` | Состояние раунда для клиентов, с `epoch` и версией. Один формат в ответах команд, `GET`, data-пакетах и метаданных |
| Публикатор | `SnapshotPublisher` | Процесс Медиа, который доставляет снимки и сообщения в LiveKit (раздел 6) |

### Чего в языке сознательно нет

- **Фазы раунда.** Автомата нет, значит нет и слова.
- **Сброса раунда.** «Сброс» есть только у таймера (`reset`) и барабана (`reset_drum`).
- **Роли.** Спикер, зритель, таймкипер — не сущности. Судья — флаг; администратор — служебные команды на сервере, а не роль в раунде.
- **Команда участника.** При входе её не выбирают.
- **Отсчёт POI.** Рука во время речи — это и есть предложение POI.
- **Перемещение одного участника судьёй.** Судья возвращает в базу только подкомнату целиком.

### Коллизии

- **Комната LiveKit** в коде называется медиакомнатой (`MediaRoom`).
- **«Спикер» в раскладке «спикер крупно»** — активный говорящий по звуку (`active_speaker` из LiveKit), а не дебатёр, который держит речь.
- **«Стол» и «позиция»** — одно и то же, в языке остаётся «позиция».
- **`join` и `enter`.** `join` — вход в раунд, `enter` — переход между комнатами.
- **`ParticipantJoined` и `participant_joined`.** Первое — наше событие входа по REST (участник в `pending`), второе — вебхук LiveKit о подключении к медиа, у нас это команда `connect`. «Выход из раунда» — это `disconnect` или `leave`.

### Технические термины

| Термин | Где | Что значит |
|---|---|---|
| `MediaGateway` | порт `round.application` | Синхронные вызовы Медиа из сценариев раунда, всегда вне транзакции: создать медиакомнату, выдать токен, наблюдать участников |
| `MediaOutbox` | порт `round.application` | Сообщения для LiveKit, которые уходят после коммита: чат, мут, выкинуть участника, закрыть медиакомнату |
| `MediaSession` | порт фронтенда | Единственный владелец подключения LiveKit на клиенте: подписки, прикрепление треков, громкость |
| Менеджер подписок | `application` фронтенда | Считает желаемые подписки по снимку и применяет их через `MediaSession` |
| `client_session_id` | клиент | Id открытой вкладки: связывает команды, телеметрию и логи |
| Режим обновления | `updating` | Агент выкатки временно отклоняет вход, пока выкатывает релиз |

## 2. Контексты

Модульный монолит: одно приложение FastAPI, внутри — модули-контексты. У каждого свой язык, своя модель и свои слои; между собой они связаны только явными интерфейсами (портами) и доменными событиями.

Граница контекста проходит по языку: отдельный контекст нужен там, где модель живёт своей жизнью и те же слова значат другое. Граница агрегата проходит по инвариантам (раздел 3).

### Раунд — ядро

Присутствие и комнаты, флаг судьи, таймеры, резолюция, руки, барабан, создание раунда и вход в него, служебные команды администратора, чат.

Чат — часть этого контекста, но отдельный агрегат и отдельный пакет `round/chat/`:
- язык общий: «участник», «комната», «раунд» в чате значат то же, что в раунде;
- жизненный цикл общий: чат живёт столько же, сколько раунд;
- будущие чаты подкомнат решают доступ по состоянию раунда (кто сейчас в комнате) — отдельный контекст постоянно ходил бы за этим в раунд;
- общих инвариантов с состоянием раунда у чата нет, поэтому агрегат отдельный: сообщение не берёт блокировку раунда и не встаёт в очередь с командами судьи.

### Медиа — антикоррупционный слой над LiveKit

Выдаёт токены, доставляет снимок раунда data-пакетами и держит его в метаданных медиакомнаты, рассылает сообщения чата и реакции, выключает микрофоны. Вебхуки и наблюдения LiveKit превращает в команды присутствия. Своя граница оправдана языком: «комната» LiveKit — это наш раунд, у «участника» там треки и подписки. Раунд про LiveKit не знает.

### Связи

- **Раунд → Медиа:** в транзакции команды раунд сигналит об изменении (`NOTIFY`, доставляется только при коммите) и кладёт сообщения для LiveKit (чат, мут) в outbox. Медиа читает снимок через порт запроса раунда и доставляет.
- **Медиа → Раунд:** вебхуки и наблюдения LiveKit становятся командами присутствия.

### Что не контекст

- **Журнал** — способ хранить доменные события, общий для модулей. Анализ по журналу (отсчёт POI, сверка с записью) станет отдельным контекстом, который журнал читает.
- **Аккаунты** — пока участник это id, имя и секрет, это часть входа в раунд. Контекст появится вместе с аккаунтами.
- **Администрирование** — служебные команды раунда с актором `admin`, а не отдельная модель.
- **Телеметрия клиентов** — инфраструктурный приём статистики WebRTC и ошибок, без доменной модели.
- **Реакции и качество связи** — модели нет: реакции бэкенд только пересылает, качество связи живёт на клиенте.

## 3. Агрегаты и инварианты

### Один агрегат `Round` на всё ядро, кроме чата

Инварианты затрагивают сразу многих участников:
- флаг судьи зависит от присутствия держателя;
- `recall(room)`, `recall_all`, «опустить все руки» — одна команда меняет многих;
- сверка присутствия с LiveKit и мягкий лимит в 30 человек — по всем участникам.

Если разрезать раунд на `Round` и `Participant`, эти правила станут транзакциями через много агрегатов или окончательно согласованными, то есть с гонками. Цена одного агрегата — очередь команд на одной блокировке и загрузка всего состояния; при 30 людях и единицах команд в секунду это миллисекунды на несколько килобайт.

Жёсткий лимит в 30 человек держит не наша блокировка, а LiveKit (`max_participants` медиакомнаты, раздел 6): вход по REST и подключение к медиа разнесены во времени, и блокировка строки их не связывает.

### Раунд живёт, пока жива ссылка

Сброса нет. Вернувшись по ссылке хоть через неделю, участники видят прежние чат, резолюцию, барабан и таймеры; судья меняет их руками.

Чтобы состояние не росло вместе с жизнью ссылки, в агрегате держатся только присутствующие и отсутствующие меньше 5 минут. Остальные выселяются в архив участников: для них ничего не меняется — вернувшись, они и так попали бы в базу с опущенной рукой (инвариант 8).

### `Round`: состояние

- участники в агрегате: имя, комната, присутствие, рука (время подъёма или её нет); не больше 40 — до 30 подключённых и свежих `pending` плюс недавно ушедшие; при переполнении первым выселяется дольше всех отсутствующий;
- вход открыт или закрыт (`entry_closed`; меняет только администратор);
- флаг судьи: держатель; последний держатель (id и имя — имя остаётся, даже если его выселили), причина и время освобождения — для «флаг свободен: <имя> отключился»;
- таймеры подготовки и речи: длительность, статус, момент окончания или остаток; номер речи; прежние таймер речи и номер — для отмены «Следующей речи»;
- резолюция и инфослайд;
- барабан: включённые позиции, выпавшие с последнего сброса, режим `remove_drawn`, последний результат (позиция и время);
- версия.

Вне агрегата — архив участников (id, имя, хеш секрета, отозван ли, время последнего входа) и сообщения чата.

### Присутствие — кэш, а не правда

Правда о том, кто подключён, — в LiveKit. Вебхуки её не гарантируют: 4 повтора, событие, пролежавшее в очереди дольше `max_age`, выбрасывается, дубли возможны; вход по REST и подключение к медиа разнесены во времени. Поэтому присутствие в агрегате — кэш со сверкой.

Состояния: `pending(since)`, `connected(sid, since)`, `disconnected(since)`. Плюс `last_ended_sid` — последняя закрытая сессия участника, чтобы опоздавший вебхук о ней её не воскресил.

| Вход | Было | Стало | Флаг и прочее |
|---|---|---|---|
| `join` | нет в агрегате (новый или из архива) | `pending(now)` | из архива — в базу, рука опущена |
| `join` | `pending` или `disconnected` | `pending(now)` | комната и рука сохраняются |
| `join` | `connected` | без изменений | вторая вкладка: флаг не трогаем, клиент спрашивает «перенести сюда?» |
| `connect(S)` | в агрегате, `S ≠ last_ended_sid` | `connected(S, now)` | — |
| `connect(S)` | нет в агрегате, есть в архиве, секрет не отозван | `connected(S, now)`, база, рука опущена | как вход из архива: клиент переподключился со старым токеном без `join` |
| `connect(S)` | секрет отозван или участник неизвестен | без изменений | Медиа после коммита выкидывает сессию (outbox) |
| `connect(S)` | `S = last_ended_sid` | без изменений | опоздавший вебхук о закрытой сессии |
| `disconnect(S)`, `leave(S)` | `connected(S)` | `disconnected(now)`, `last_ended_sid = S` | держатель → `JudgeFlagReleased(holder_disconnected)` |
| `disconnect(S)`, `leave(S)` | `pending`, `S ≠ last_ended_sid` | `disconnected(now)`, `last_ended_sid = S` | так же приходит `participant_connection_aborted`: ICE не установился |
| `disconnect(S)`, `leave(S)` | `connected(S′)`, `S′ ≠ S` | без изменений | старая сессия закрылась после новой |
| `disconnect(S)`, `leave(S)` | `disconnected`, или `S = last_ended_sid`, или нет в агрегате | без изменений | опоздавшее закрытие уже закрытой сессии |
| `disconnect` с причиной `DUPLICATE_IDENTITY` | — | без изменений | это замена сессии, а не выход |
| `sync_presence(observed, at)` | `connected(S)`, участника не видно вовсе | `disconnected(now)`, `last_ended_sid = S` | держатель → `JudgeFlagReleased(holder_disconnected)` |
| `sync_presence(observed, at)` | `connected(S)`, виден с `S′ ≠ S` | `connected(S′, now)` | вторая вкладка уже заменила сессию: флаг не трогаем |
| `sync_presence(observed, at)` | `pending` или `disconnected`, виден с сессией `S` | `connected(S, now)` | — |
| время | `pending` дольше 30 с от `since` | считается отключённым с `since` | для лимита, `claim_judge` и выселения; в снимке остаётся `pending` с `since`; без события |
| время | `disconnected` или `pending` дольше 5 минут от `since`, или агрегат переполнен | выселен в архив | `ParticipantEvicted`; лениво, при любой команде раунда |

**Сверка.** `observed` — участники медиакомнаты из `ListParticipants`, снятые до транзакции с таймаутом ~1 с; `at` — момент снятия. Строки сверки применяются только к тем, чьё присутствие не менялось после `at`: вебхук, пришедший между наблюдением и блокировкой, не перетирается. Медиакомнаты нет — наблюдение пустое. Наблюдение не удалось (таймаут или ошибка) — сверки нет: `claim_judge` при занятом флаге получает `judge_flag_taken`, от `pending` — `not_connected`. Когда сверяемся:
- `claim_judge` при занятом флаге — держателя, которого LiveKit не видит, отключаем и флаг отдаём просящему;
- `claim_judge` от `pending` — если LiveKit его уже видит, он становится `connected`;
- старт бэкенда — для раундов с живой медиакомнатой (`room_sid` в `media_rooms` и медиакомнаты из `ListRooms`): это обязательная часть восстановления, а не страховка;
- `room_started`.

**`leave`** шлёт клиент при закрытии вкладки, с `sid` своей сессии. Вкладка, выбитая второй вкладкой, `leave` не шлёт.

### `Round`: инварианты

1. Судья один. Флаг можно взять, только если у него нет держателя; захват атомарен. Взять флаг может только `connected` участник (для `pending` — сначала сверка).
2. Держатель перешёл в `disconnected` — флаг сразу свободен (`JudgeFlagReleased`, причина `holder_disconnected`) и сам не возвращается. Всем видно «флаг свободен: <имя> отключился», вернувшемуся — заметная кнопка «взять снова». Короткие провалы связи, примерно до 15–20 с, LiveKit переживает без выхода. Сон ноутбука, долгая плохая связь с включённой камерой, неудачное возобновление — полное переподключение, флаг теряется; поэтому держателю флага подсказка «выключите камеру» показывается раньше, чем остальным (раздел 7).
3. Судейские команды принимаются только от держателя флага: таймеры, резолюция, барабан, микрофоны, возврат в базу, чужие руки. Проверяет сам агрегат — каждая команда знает, кто её отдал.
4. Передать флаг можно только `connected` участнику. Передача себе ничего не делает.
5. Каждый участник ровно в одной комнате. Перейти можно в любую, лимита нет.
6. `recall` — только для подкомнат. Двигает всех, кто числится в комнате, включая отключённых: иначе вернувшийся окажется один в пустой OG. `recall(JUDGES)` уводит в базу и самого судью.
7. Мягкий лимит: вход — и новый, и повторный — отклоняется (`round_full`), если `connected` и свежих `pending` уже 30 (входящий не считается). Жёсткий лимит — у LiveKit. Закрытый вход (`entry_closed`) отклоняет новых участников; повторный вход по id и секрету — нет.
8. Повторный вход по id и секрету — тот же участник. Если он ещё в агрегате (отсутствовал меньше 5 минут) — своя комната, рука как была; из архива — база, рука опущена. Флаг не возвращается. Имя из повторного входа заменяет прежнее в агрегате и в архиве.
9. Рука: повторный подъём ничего не меняет. Очередь — по времени подъёма и считается по комнате. Рука переходит вместе с человеком. Отключённые в очереди не показываются, время подъёма у них хранится. Опустить руку ушедшего можно.
10. Барабан: `draw` тянет из включённых позиций, в режиме `remove_drawn` — из невыпавших. Тянуть не из чего — ошибка `drum_empty` («барабан пуст — сбросьте»); сам себя барабан не сбрасывает. Без `remove_drawn` выпавшие не копятся. `configure_drum` выпавших не сбрасывает. Выключить все позиции можно. Последний результат хранится до `reset_drum`.
11. Таймер: `start` на идущем и `pause` на паузе ничего не делают. `set` задаёт остаток при прежней длительности (интерфейс речи показывает и вводит прошедшее время); на остановленном таймере переводит его в паузу с этим остатком, на идущем — отсчёт продолжается. `reset` — к длительности, таймер остановлен. `configure_timer` меняет длительность (подготовка — 1–30 минут, речь — 1–15 минут) и сбрасывает таймер; защищённое время и сигналы считаются от длительности. После конца (у речи — после грейса) показывается перерасход. У подготовки сигналов нет, как в спеке.
12. «Следующая речь» увеличивает номер речи и сбрасывает таймер речи к длительности, остановленным. Прежние таймер (со статусом и моментом окончания) и номер сохраняются: `undo_next_speech` возвращает их как были — если таймер шёл, он идёт дальше, будто кнопку не нажимали.
13. Выключить микрофон можно участнику в любой комнате. У мута в `Round` нет состояния — микрофон живёт в LiveKit: агрегат проверяет полномочия и пишет событие, мут выполняет Медиа после коммита.
14. Размер: имя — 1–40 символов и не больше 80 байт UTF-8, после обрезки пробелов, без управляющих символов; резолюция — до 300 символов и 600 байт; инфослайд — до 1500 символов и 3000 байт; в агрегате не больше 40 участников. Снимок с максимальными значениями укладывается в 14 КиБ (раздел 9).

### Время и случайность

`now` и случайный выбор для `draw` агрегат получает аргументами — от портов `Clock` и `RandomSource`. Правила остаются чистыми и детерминированными в тестах.

### Повторы команд

- Каждая HTTP-команда раунда несёт ключ идемпотентности от клиента; у сверки и служебных команд ключа нет. Первым действием транзакции ключ вставляется в `command_keys` вместе с хешем запроса; уникальность — в пределах раунда и участника. Одновременный повтор ждёт на уникальном индексе, пока первый запрос не закоммитится, получает конфликт и возвращает текущий снимок; тот же ключ с другим запросом — `422`. Пока запрос идёт, кнопка в интерфейсе заблокирована.
- `expected_version` не используем: версию двигает любое действие любого участника, и судейские команды постоянно отбивались бы.
- Дубли вебхуков отсекаются по `id` события (он одинаков у всех повторов) в той же таблице. На вебхуки, которые домен отклонил, отвечаем 2xx: иначе LiveKit повторяет запрос и держит очередь всей комнаты.

### Служебные команды администратора

Администратор — автор площадки — выполняет их на сервере через CLI: `just admin <команда> <round_id> [<participant_id> | <message_id>]` → `docker compose exec backend python -m debatemeet.admin …`. `justfile` для сервера приезжает в бандле развёртывания. Интерфейса и ролей нет. В журнале актор — `admin`.

- `admin_show_round` — прочитать раунд: участники (id, имя, комната, присутствие), держатель флага, последние сообщения с id. С неё начинается любое вмешательство;
- `admin_release_judge` — освободить флаг (причина `admin`): держатель забыл ноутбук с открытой вкладкой, пересел на телефон;
- `admin_remove_participant` — убрать участника: выселить из агрегата, отозвать секрет, выкинуть из медиакомнаты через outbox; если он держал флаг — флаг освобождается с причиной `admin`;
- `admin_close_entry`, `admin_open_entry` — закрыть или открыть вход новым участникам;
- `admin_delete_messages` — удалить сообщение или все сообщения участника; клиенты получают `chat_deleted`;
- `admin_delete_round` — удалить раунд: состояние, архив участников, сообщения; медиакомната закрывается через outbox. Журнал остаётся — в нём только id.

Удаление данных по просьбе человека делается этими же командами.

### `Message` — агрегат чата

Сообщение не редактируется; удалить его может только администратор. Общего состояния у чата нет, порядок задаёт серверный счётчик. Инварианты:
- текст — 1–1000 символов: с запасом помещается в надёжный data-пакет LiveKit (до 15 КиБ);
- автор — участник раунда; проверяется чтением раунда без блокировки: атомарность с остальным раундом не нужна. Системная строка — исключение: у неё автора нет;
- лимит частоты на участника считается в Postgres: процессов бэкенда может быть несколько;
- идемпотентность — ключ вставляется первым шагом (`INSERT … ON CONFLICT DO NOTHING`), блокировки раунда нет.

Системная строка о результате барабана создаётся по `PositionDrawn` в той же транзакции: результат жеребьёвки и строка в чате не расходятся. До клиентов обе доходят через outbox Медиа (раздел 6).

История: при открытии раунда клиент загружает последние 50 сообщений, более ранние — по кнопке (раздел 5).

## 4. Слои и паттерны бэкенда

### Структура пакетов

```
backend/src/debatemeet/
  shared/
    domain/            DomainEvent, DomainError
    application/       порты Clock, RandomSource, UnitOfWork
    infrastructure/    Postgres и реализация UnitOfWork, журнал, command_keys, rate_limits, system (epoch), настройки, логи
    api/               общие эндпоинты: /api/time, /api/health, /telemetry, /client-errors
  round/               контекст «Раунд»
    domain/            Round, объекты-значения (Timer, Drum, Motion, Room, Position), события, ошибки
    application/       use cases; порты RoundRepository, ParticipantRegistry, SnapshotQuery, ChangeNotifier, MediaGateway, MediaOutbox
    infrastructure/    репозитории на Postgres, журнал, NOTIFY
    api/               роутеры FastAPI, проверка секрета участника
    contract/          схемы Pydantic: снимок, ответы, конверт серверных пакетов; перевод домена в снимок
    chat/              агрегат Message: domain/, application/, infrastructure/, api/
  media/               контекст «Медиа»
    application/       публикатор, реализация MediaGateway, разбор вебхуков; порт LiveKitApi
    infrastructure/    клиент LiveKit (реализация LiveKitApi), реализация MediaOutbox, таблицы media_rooms и media_outbox
    api/               приём вебхуков LiveKit
  main.py              корень композиции для HTTP
  admin.py             корень композиции для служебных команд (CLI)
```

### Правила зависимостей

Проверяются `import-linter` в CI; контракты учитывают косвенные импорты.

1. `domain` ни от чего не зависит: ни FastAPI, ни SQLAlchemy, ни Pydantic, ни LiveKit, никакого ввода-вывода. Чистый синхронный Python на dataclasses. `now` и случайность агрегат получает аргументами.
2. `application` зависит только от `domain` и `shared`; порты объявляет сам (`Protocol`).
3. `infrastructure` реализует порты; зависит от `application`, `domain` и `shared.infrastructure` — общего соединения, в одной транзакции которого пишут раунд, чат и outbox Медиа.
4. `api` вызывает `application`, схемы берёт из `contract`; в `domain` смотрит только за типами ошибок и значений, в `infrastructure` не ходит.
5. `contract` — формат на границе: Pydantic и перевод доменного объекта в снимок. Читает `domain`, больше ни от чего не зависит.
6. `round.chat` видит раунд только через `round.application` (запрос «участник ли автор»), в его домен не заходит.
7. Раунд не знает о Медиа. Медиа видит раунд только через `round.application` и `round.contract`; косвенный путь `contract → domain` разрешён явно.
8. Всё встречается только в корнях композиции — `main.py` и `admin.py`.

### Путь одной команды

```
POST /api/rounds/{id}/drum/draw
→ api: проверить секрет участника → команда Draw(round_id, by)
→ application, одна транзакция (Unit of Work):
    command_keys ← ключ идемпотентности       повтор → текущий снимок
    round = repo.get_for_update(round_id)     SELECT … FOR UPDATE
    round.draw(by, now, pick)                 правила домена; агрегат копит события
    repo.save(round)                          версия +1
    события → журнал; обработчики внутри транзакции (PositionDrawn → системная строка → outbox)
    NOTIFY round_changed                      доставляется только при коммите
  commit
→ api: 200 со снимком, или ошибка домена → 403 / 404 / 409 с кодом
→ публикатор Медиа догоняет версию и доставляет снимок и outbox
```

### Паттерны

| Паттерн | Где | Зачем |
|---|---|---|
| Агрегат | `Round`, `Message` | Граница консистентности |
| Объект-значение | `Timer`, `Drum`, `Motion`, `Room`, `Position`, id | Неизменяемы, правила внутри: например, `Timer.remaining(now)` |
| Фабрика | `Round.create` | Начальное состояние: шесть комнат, таймеры по умолчанию, все позиции в барабане |
| Доменное событие | события раунда | Журнал, реакции внутри транзакции |
| Репозиторий | порт в `application`, реализация в `infrastructure` | Загрузить агрегат под блокировкой и сохранить |
| Unit of Work | порт в `shared.application`, реализация в `shared.infrastructure` | Одна транзакция на команду: агрегат, журнал, системная строка, outbox |
| Transactional outbox | `media_outbox` | Сообщения для LiveKit уходят только после коммита и с повторами |
| Прикладной сервис | `application` | Одна команда — один сценарий |
| Порты и адаптеры | вся граница ядра | Домен не знает про Postgres и LiveKit |
| Антикоррупционный слой | `media` | Перевод между нашим языком и LiveKit |
| CQRS-lite | `application` | Команды идут через агрегат под блокировкой; снимок строится из доменного объекта, прочитанного без блокировки; история чата — запросом мимо домена |
| Корень композиции | `main.py`, `admin.py` | Ручная сборка зависимостей, без DI-контейнера: адаптеров единицы |

### Сознательно не берём

- **Event sourcing.** Журнал пишем, но состояние из него не восстанавливаем: понадобились бы версионирование событий и проекции.
- **Шину команд и медиатор.** Эндпоинт вызывает use case напрямую.
- **Саги и process manager.** Долгих процессов нет.
- **Specification.** Правил, которые надо комбинировать, нет.
- **Доменные сервисы.** Пока нет правила, которое не ложится ни в один агрегат; появится — заведём.
- **Роли и права.** Сознательно отложены; администратор — это служебные команды на сервере.

### Ещё решения

- **Pydantic — только на границе:** схемы API и снимка (`round/contract`) и настройки (`pydantic-settings`). Формат API меняется, не трогая домен.
- **Ошибки домена — исключения с кодом** (`DomainError("drum_empty")`). API превращает их в HTTP-ответ, фронтенд показывает текст по коду.

## 5. Персистентность и конкурентность

### `Round` — JSONB-документ

Раунд всегда загружается целиком, весит несколько килобайт, искать внутри него запросами не нужно — для анализа есть журнал. Нормализованная схема означала бы таблицы на участников, таймеры и барабан плюс слой отображения на доменные объекты. JSONB оставляет домен свободным: dataclasses переводятся в JSON и обратно явным маппером в `infrastructure`. Цена — в документе нет ограничений на уровне базы; целостность держат домен и тесты маппера.

### Таблицы

| Таблица | Чья | Что в ней |
|---|---|---|
| `rounds` | Раунд | `id` (128 бит из ссылки), `state` (JSONB с номером схемы), `version`, время создания и изменения |
| `participants` | Раунд | Архив участников: `round_id`, `participant_id`, имя, хеш секрета, отозван ли, время последнего входа. Секрет — забота входа, в агрегат и снимок не попадает |
| `messages` | Раунд (чат) | Счётчик-id, `round_id`, автор (у системной строки пусто), имя автора, вид (обычное или системное), текст, время |
| `event_log` | общий | Счётчик-id, `round_id`, версия раунда после события, тип, данные, актор (участник, `admin` или система), серверное время |
| `command_keys` | общий | `round_id`, `participant_id`, ключ, хеш запроса, версия после команды, время. Уникальность — `(round_id, participant_id, ключ)`, индекс `NULLS NOT DISTINCT`. Для вебхуков ключ — id события, `participant_id` может быть пуст |
| `media_rooms` | Медиа | `round_id`, `room_sid` живой медиакомнаты (пусто, если её нет), выгруженные версии для data-пакетов и для метаданных, время последней записи метаданных |
| `media_outbox` | Медиа | Сообщения для LiveKit: чат, системные строки, удаление сообщений, мут, просьба включить микрофон, выкинуть участника, закрыть медиакомнату. Пишутся в транзакции команды, доставляются после коммита |
| `rate_limits` | общий | Ключ (IP или участник), окно, счётчик |
| `telemetry` | общий | Пачки клиентской телеметрии и отчёты об ошибках; 30 дней |
| `system` | общий | Одна строка: `epoch` — меняется при восстановлении из бэкапа |

В `event_log` имён нет, даже в данных событий: `MessagePosted` хранит id сообщения, а не текст. Журнал хранится без срока — в нём только id и события.

Id раунда — это ключ доступа. В логах и метриках он пишется только хеш-префиксом; access-логи Caddy и uvicorn маскируют путь раунда. Caddy отдаёт `Referrer-Policy: no-referrer`: ссылка раунда не уходит на другие сайты в заголовке `Referer`. Имя медиакомнаты (это тот же id) в логах LiveKit — принятый риск.

### Как выполняется команда

```
(до транзакции, если нужно: наблюдение LiveKit с таймаутом ~1 с)
BEGIN
  SET LOCAL lock_timeout = '2s'                   превышение → 503 round_busy
  INSERT INTO command_keys … ON CONFLICT DO NOTHING RETURNING
      конфликт → дождаться первого, вернуть текущий снимок (другой хеш → 422)
  SELECT state, version FROM rounds WHERE id = $1 FOR UPDATE
  → маппер → Round → выселение по времени → метод агрегата → события
  UPDATE rounds SET state = …, version = version + 1
  INSERT INTO event_log …; INSERT INTO messages …; INSERT INTO media_outbox …
  NOTIFY round_changed, '<round_id>'
COMMIT
```

- Уровень изоляции — READ COMMITTED: блокировка строки сериализует команды одного раунда, оптимистичные повторы не нужны. Через блокировку проходят все писатели раунда: команды, вебхуки, сверка присутствия, служебные команды.
- Сетевых вызовов к LiveKit под блокировкой строки нет: наблюдение — до транзакции, создание медиакомнаты, мут и рассылка — после коммита. `idle_in_transaction_session_timeout` — 5 с.
- Сообщение чата блокировку раунда не берёт: вставляет ключ, читает раунд без блокировки, пишет сообщение и outbox, `NOTIFY`.
- Обслуживание — удаление ключей старше суток, телеметрии старше 30 дней, старых окон лимитов — идёт фоновым циклом публикатора (раздел 6), а не внутри команд.

### Порядок и история чата

Id сообщения не гарантирует порядок коммитов: позже закоммиченное сообщение может получить меньший id. Поэтому клиент склеивает историю и живые сообщения по id, а не доверяет курсору.

- При открытии раунда — последние 50 сообщений; более ранние — страницами назад по id. Старые сообщения все закоммичены, пропусков при листании назад нет.
- После долгого разрыва — догрузка вперёд от последнего известного id с перекрытием, затем склейка по id.
- Удалённое администратором сообщение исчезает у клиентов по пакету `chat_deleted`.

### Версия и epoch

Версия растёт на единицу с каждой закоммиченной командой и никогда не переиспользуется. Восстановление из бэкапа откатывает версии назад, поэтому в снимке есть ещё `epoch` из таблицы `system`: ранбук восстановления меняет его. Клиент сравнивает пару (epoch, version): новый epoch принимается безусловно.

### Формат документа

У документа есть номер схемы. Неизвестная или более новая схема — это `503` и алерт, а не сброс: пути «начать заново» нет. Документ меняется по тому же expand → contract, что и таблицы: релиз N читает старую и новую схемы, а пишет старую; новую начинает писать N+1. Так откат кода на одну версию никогда не встречает непонятный ему документ. CI держит документ-фикстуру для каждой версии схемы и проверяет, что код N читает документы N+1.

### Прочее

- SQLAlchemy Core без ORM: доменные объекты через ORM не отображаем, свой Unit of Work уже есть. Миграции схемы — Alembic.
  - Одна история на всю базу — `debatemeet/migrations/`. Ревизии пишутся руками через `op`: ORM-метаданных для сравнения нет. Имена ревизий по порядку, `just migration 0002 "…"`.
  - Применяет их только `python -m debatemeet.migrate` — отдельная точка сборки, как `main.py`. Весь подъём идёт в одной транзакции: Postgres умеет транзакционный DDL.
  - Если в базе ревизия, которой нет в истории образа, база впереди образа: это откат кода. Миграции совместимы с прежним кодом (expand → contract), поэтому базу не трогают, пишут предупреждение и выходят с кодом 0. Не 0 — только ошибка: агент считает релиз упавшим.
  - Отката схемы нет: `downgrade` у ревизий бросает исключение.
- Время — из порта `Clock`, не из `now()` базы: один источник, подменяется в тестах. Хранится как `timestamptz` в UTC.
- id раунда — 128 случайных бит, 22 символа в ссылке; он же ключ доступа.
- id участника (12 символов, публичный: его видят все в медиакомнате) и секрет (256 бит) выдаёт сервер при первом входе; в базе от секрета — только SHA-256. Браузер хранит пару «id + секрет» для каждого раунда, имя — одно на все раунды. Повторный вход — по этой паре; без неё или с id, которого сервер не знает (например, после восстановления старого бэкапа), — новый участник. Администратор может отозвать секрет.
- Аккаунты потом привязываются к участнику одной колонкой в `participants`.

## 6. Интеграция с LiveKit

Контекст «Медиа» — антикоррупционный слой: домен и сценарии раунда не знают, как состояние доставляется до клиентов. Факты о LiveKit ниже проверены по исходникам livekit-server 1.13.7 и livekit-client 2.22.3 при ревью.

### Доставка состояния: снимок и поток обновлений

LiveKit прямо пишет: метаданные и атрибуты не подходят для обновлений чаще раза в несколько секунд — синхронизация на сервере дорогая; для частых обновлений — data-пакеты. Атрибуты у LiveKit предназначены для состояния, которое участник пишет сам о себе, а у нас всё пишет сервер и правила общие. Поэтому:

- **Быстрый путь.** На каждое изменение сервер рассылает всем полный `RoundSnapshot` надёжным data-пакетом (тема `state`, с `nonce` для отсечения повторов). Снимок укладывается в 14 КиБ (инвариант 14) при лимите пакета 15 КиБ; задержка — десятки миллисекунд.
- **Опорное состояние.** Тот же снимок лежит в метаданных медиакомнаты. Пишется не чаще раза в 2 с и всегда догоняет последнюю версию. Его читают подключающиеся и переподключающиеся.
- **Клиент** берёт снимок с наибольшей парой (epoch, version) из любого источника: ответ команды, пакет, метаданные, `GET`. Потерянный или пришедший не по порядку пакет безвреден — каждый пакет полный.
- **Ограниченная устарелость.** «Надёжный» пакет не гарантирует доставку каждому: если запись медленному получателю не укладывается в 50 мс, LiveKit пакет выбрасывает. Поэтому клиент раз в 15 с спрашивает `GET /snapshot?epoch=…&since=<version>` (ответ `304`, если совпадают epoch и версия) и после любого переподключения запрашивает снимок.
- **Атрибуты участников не используем.** Комнаты и руки участников — внутри снимка. Клиент склеивает список подключённых из LiveKit со снимком по id участника.
- **Дельты не нужны:** полный снимок проще и не требует обработки пропусков. Размер ограничен доменом (не больше 40 участников в агрегате). Если состояние всё же вырастет — дельты с версией, контракт тот же.
- **Клиенты не могут слать data-пакеты вообще:** в токене нет `canPublishData`, и LiveKit отбрасывает такие пакеты на сервере. Иначе любой участник подделал бы снимок с огромной версией и заморозил раунд у всех: клиент не отличает пакет сервера от пакета участника, которого ещё не знает. Поэтому реакции идут через бэкенд. Клиент дополнительно принимает только темы из белого списка и проверяет пакет по схеме.

Отказ от атрибутов закрывает класс проблем: `recall_all` из 30 отдельных записей, ложащихся поверх более позднего перехода; «not found» для переподключающегося участника; атрибуты из старого токена при полном переподключении; отсутствие общей версии.

### Медиакомната

- Имя медиакомнаты — id раунда. Создаёт её только `join` — после коммита, до выдачи токена: `CreateRoom` с текущим снимком в метаданных и `max_participants = 30`. Для уже живой комнаты `CreateRoom` возвращает её как есть, поэтому снимок следом пишет публикатор.
- `room.auto_create: false`. Иначе клиент со старым токеном (проснувшийся ноутбук) сам создал бы закрытую комнату — без метаданных и без лимита. С выключенным автосозданием он получает ошибку и делает REST-`join`, который создаёт комнату правильно. Глобальный `room.max_participants: 30` — страховка.
- Когда все ушли, LiveKit через ~20 с (`departure_timeout`) закрывает медиакомнату вместе с метаданными: на одном узле хранилище комнат — в памяти. Раунд при этом жив; следующий `join` создаёт медиакомнату заново из базы.
- Публикатор комнаты не создаёт: поздний вебхук или `GET` не должны воскрешать пустую комнату.

### Публикатор

Среди процессов бэкенда один лидер: он держит `pg_try_advisory_lock(PUBLISHER)` на отдельном соединении. Упал лидер — соединение закрылось, блокировку берёт другой процесс. Состояние доставки лежит в базе, а не в памяти, поэтому при смене лидера ничего не теряется.

```
лидер: LISTEN round_changed; просыпается по NOTIFY и раз в секунду
  раунды, где version > data_version, или метаданные отстали и с прошлой записи прошло ≥ 2 с,
    или в media_outbox есть недоставленное
  для каждого раунда, по порядку:
    прочитать снимок заново (SnapshotQuery) — всегда последний, а не тот, что был при уведомлении
    SendData(state)                           data_version = version
    прошло ≥ 2 с с записи метаданных?  → UpdateRoomMetadata; metadata_version = version
    доставить outbox по порядку               отметить доставленное; ошибка → повтор с паузой
  фоновое обслуживание: старые ключи, телеметрия, окна лимитов
```

- `room_finished` или ответ LiveKit «комнаты нет» обнуляют `room_sid` в `media_rooms`. Раунды без `room_sid` публикатор пропускает: доставка ждёт, пока `join` создаст медиакомнату.
- `room_started` записывает новый `room_sid` и обнуляет уровни доставки: снимок и метаданные выгружаются целиком, запускается сверка присутствия.
- Инициатору команды снимок приходит в её ответе, он не ждёт рассылки.

### Токены

- Identity — id участника, name — его имя.
- Права: войти в медиакомнату раунда; публиковать только камеру и микрофон; подписываться. Слать data-пакеты и менять свои метаданные и атрибуты нельзя. В токене же — настройки комнаты с `max_participants = 30` на случай, если комнату создаст токен.
- Срок жизни — 10 минут; подключённым LiveKit продлевает токены раз в 5 минут сам. После сна дольше 10 минут переподключение получает `401`: клиент на `Disconnected` делает `POST /join` с id и секретом и подключается заново. Исключения — причины `DUPLICATE_IDENTITY` (вкладку заменила другая), `CLIENT_INITIATED` (клиент сам закрыл сессию, в том числе по «Вы ещё здесь?» — экран «вы вышли» с кнопкой «вернуться»), `PARTICIPANT_REMOVED` и `ROOM_DELETED`. Отказ повторного входа: `401` (секрет отозван) — экран «вас убрали из раунда»; `404` — раунд удалён.

### Вебхуки

- На серверах LiveKit работает в host-сети и шлёт вебхуки в бэкенд на `127.0.0.1:8000`, минуя Caddy и TLS. В разработке и CI — на `host.docker.internal:8000`: у сервиса livekit в compose `extra_hosts: ["host.docker.internal:host-gateway"]`, бэкенд слушает `0.0.0.0`.
- Подпись проверяется. Дубли отсекаются по `id` события в `command_keys`.
- Перевод в команды:
  - `participant_joined` → `connect(id, sid)`;
  - `participant_left` и `participant_connection_aborted` → `disconnect(id, sid)`;
  - выход с причиной `DUPLICATE_IDENTITY` пропускается — это замена сессии;
  - `room_started` → новый `room_sid`, полная выгрузка и сверка присутствия;
  - `room_finished` → `room_sid` обнуляется;
  - остальное игнорируется.
- Ответ — 2xx, что бы ни решил домен. 5xx — только если недоступна наша база (тогда повторы LiveKit полезны), 401 — при неверной подписи.
- Доставка не гарантирована. Повторов 4, суммарно ~15 с, и это не настраивается; очередь — на комнату, с одним обработчиком. `webhook.resource_url_notifier.max_age` (по умолчанию 30 с) ограничивает только ожидание в очереди до отправки — поднимаем до 5 минут. Событие, которое отправлялось, пока бэкенд лежал, всё равно теряется, поэтому сверка присутствия на старте бэкенда обязательна. Алерт — на `livekit_webhook_dispatch_total` с неуспешным статусом.

### Поведение LiveKit, на которое опирается модель

- `participant_joined` приходит после установки ICE, а не при сигнализации. Если ICE не установился — приходит `participant_connection_aborted` без предшествующего `joined`.
- Возобновление сохраняет SID и вебхуков не шлёт; разрыв без выхода переживается примерно 15–20 с.
- Полное переподключение (сон ноутбука, качество `LOST` 10 с при публикации, неудачное возобновление) — это `left` и новый `joined` с новым SID; `RemoteParticipant` на клиентах пересоздаются.
- Вторая сессия с той же identity выбивает первую с `DUPLICATE_IDENTITY`; выбитый клиент сам не переподключается.
- `ListRooms.num_participants` обновляется раз в 5 с, `ListParticipants` — сразу: для решений используем второе.

### Остальные каналы

- **Чат.** Через outbox: надёжный пакет `chat` всей медиакомнате; удаление — пакет `chat_deleted`. После переподключения клиент догружает сообщения и склеивает по id.
- **Мут.** Через outbox после коммита: Медиа находит микрофонный трек участника и выключает его (`MutePublishedTrack`, нужен sid трека и право `roomAdmin` у серверного ключа). Удалённое включение микрофона выключено (`enable_remote_unmute` не включаем). Просьба включить — пакет `request_unmute` этому участнику; у него появляется подсказка «Судья просит включить микрофон».
- **Реакции.** `POST /reactions` → бэкенд сразу, без базы, шлёт lossy-пакет `reaction` участникам комнаты отправителя (`destinationIdentities` по снимку). Лимит частоты — в памяти процесса: реакции и так без гарантий.
- **Подписки** — целиком на клиенте (раздел 7); сервер их не принуждает. Приватность комнат через разрешения на подписку — после MVP.

### Конфигурация LiveKit

- `rtc.node_ip` задан явно, `use_external_ip: false`: иначе LiveKit узнаёт свой адрес через публичный STUN, по умолчанию зарубежный. UDP mux — 7882, ICE/TCP — 7881, TURN/TLS — 443.
- Порт 7880 и порт Prometheus (6789) слушают только `127.0.0.1` (`bind_addresses`), наружу — через Caddy. ICE/TCP и UDP слушают все интерфейсы, так и нужно. Порт TURN 5349 LiveKit сузить не умеет: снаружи его закрывает файрвол, а Caddy ходит на него по `127.0.0.1`.
- TURN/TLS делит 443 с HTTPS. Caddy с модулем layer4 — образ `livekit/caddyl4`, на нём же построен `livekit/generate` — стоит обёрткой слушателя на 443. Соединение с SNI домена TURN он забирает раньше HTTP-сервера, снимает TLS и передаёт TCP на `127.0.0.1:5349` (`turn.external_tls`). Остальные соединения идут к сайтам, и те видят настоящий адрес клиента. TURN/UDP выключен: его порт закрыт, UDP-медиа идут через 7882.
- `room.auto_create: false`, `room.max_participants: 30`, `departure_timeout` — по умолчанию.
- `limit.subscription_limit_video` ≈ 12; `sync_streams` не включаем.
- `webhook`: адрес бэкенда, `resource_url_notifier.max_age: 5m`.
- Ключи — только из окружения (`LIVEKIT_KEYS`), не в бандле и не в репозитории. Ключей может быть несколько — для ротации: первый — ключ бэкенда, он же подписывает вебхуки, следом уходящие.
- dev-ключ из `deploy/dev/livekit.yaml` открыт всем, поэтому на серверах от него отказываются оба. LiveKit запускает `deploy/server/livekit/livekit.sh`, и тот не стартует, если dev-ключ есть в `LIVEKIT_KEYS`. Бэкенд на `stage` и `prod` не принимает его при чтении настроек.
- Файл конфига общий для стенда и прода (`deploy/server/livekit/livekit.yaml`). Значения сервера — адрес узла, домен TURN, ключ вебхуков — приходят переменными окружения: у каждого поля конфига LiveKit есть своя.

### Проверки на стенде

К списку из ресерча добавляются проверки ниже. Каждую, кроме `caddy reload`, сначала гоняют локально на dev-стеке — в срезе, где появляется её функция, — и повторяют на стенде в срезе С:
- бэкенд перезапущен, пока люди входят и выходят, — присутствие сходится;
- полное переподключение (сон ноутбука) — человек возвращается в свою комнату, флаг освобождается; сон дольше 10 минут — клиент сам входит заново;
- вторая вкладка — первая не выпадает молча;
- `recall_all`, пока кто-то переходит в другую комнату, — итог в базе и у всех клиентов одинаковый;
- всплеск команд (все расходятся по комнатам) — метаданные пишутся не чаще раза в 2 с, звук после перехода появляется не позже чем через 1 с;
- бот пытается отправить data-пакет — он никому не доходит;
- лидер-публикатор убит посреди выгрузки — другой процесс подхватывает, клиенты догоняют последнюю версию;
- `caddy reload` не рвёт TURN/TLS.

## 7. Фронтенд

### Гексагон, как на бэкенде

Самый опасный класс багов из спеки — звук подготовки слышен в базе — живёт не в интерфейсе, а в логике подписок. Feature-Sliced Design раскладывает интерфейс по фичам, но не изолирует медиа и состояние от React; гексагон изолирует, и модель на обеих сторонах одна.

```
frontend/src/
  contract/        сгенерировано из OpenAPI: снимок, команды, конверт серверных пакетов
  domain/          чистый TS: правила отображения над снимком
  application/     сценарии клиента, стор, менеджер подписок, порты
  infrastructure/  сессия LiveKit, клиент API, синхронизация часов, телеметрия, localStorage
  ui/              React: страницы, виджеты, селекторы
  main.tsx         корень композиции: собирает адаптеры
```

- **`contract`** — опубликованный язык сервера и клиента; доступен всем слоям. Своих копий типов не заводим.
- **`domain`**: сколько осталось или прошло на таймере с поправкой часов, горит ли защищённое время, когда сигналы, номер руки в очереди, кто в моей комнате, на кого я должен быть подписан. Клиент ничего не решает за сервер — только вычисляет отображение.
- **`application`**: сценарии (войти, перейти в комнату, взять флаг…), стор на Zustand, менеджер подписок. С медиа работает через порт `MediaSession`, не зная LiveKit.
- **`infrastructure`**: адаптер `MediaSession` на `livekit-client` — единственный владелец подписок, прикрепления треков и громкости; `openapi-fetch`; запросы времени; `getStats()`; localStorage с try/catch.
- **`ui`**: читает стор и вызывает сценарии. Треки рисуют тонкие свои компоненты, которые получают трек от `MediaSession` и вызывают `track.attach(el)`. `@livekit/components-react` не используем: его компоненты сами управляют подписками (`VideoTrack` вызывает `setSubscribed`, `RoomAudioRenderer` владеет звуком) и становятся вторым владельцем.

Правила зависимостей те же, что на бэкенде; проверяются `dependency-cruiser` в CI.

### Поток данных — однонаправленный

```
LiveKit: data (снимок, чат,   ┐
         реакции)             │
LiveKit: метаданные (снимок) ─┼─→ стор ─→ ui
LiveKit: треки, кто говорит,  │     │
         качество связи ──────┤     └─→ менеджер подписок ─→ MediaSession
REST: ответы команд, история, ┘
      GET снимка раз в 15 с
ui ─→ сценарий ─→ REST-команда ─→ сервер
```

- Оптимистичных обновлений нет, решает сервер. Инициатор команды сразу применяет снимок из её ответа, остальные получают его пакетом; стор берёт наибольшую пару (epoch, version). Пустые или битые метаданные игнорируются.
- **Кого слушать.** Желаемые подписки = участники, подключённые в LiveKit, ∩ участники снимка, у которых комната — моя. Присутствие в снимке на это не влияет: ложный `disconnected` не должен никого заглушить. Кого нет в снимке, того не слушаем.
- **Порядок при переходе.** Сначала локально заглушить старую комнату → снять подписки на её звук и подписаться на звук новой одной пачкой → для видео сначала отписка, потом подписка (при `subscription_limit_video` лишние подписки ждут свободного слота) → показать новую комнату. Шаги сверяются с последней версией: шаг от устаревшей версии отменяется; ожидание `TrackSubscribed` — не больше 500 мс.
- На звук подписаны все участники моей комнаты, всегда; на видео — только те, чьи плитки нарисованы, остальные — аватары без трафика. Плитка «спикер крупно» выбирается из уже подписанных, с гистерезисом, чтобы подписки не дёргались на каждую смену говорящего; слой меняет adaptiveStream.
- Громкость каждого участника (`setVolume`) заново применяется из localStorage на `TrackSubscribed`: полное переподключение пересоздаёт `RemoteParticipant`.
- Если моя комната сменилась на базу в снимке, который пришёл не ответом на мою команду, — заметный баннер «вас вернули в базу».
- Уведомления в подкомнате о вошедших и вышедших клиент выводит сам, из смены комнат между снимками; сервер для них ничего не шлёт. Первый снимок после входа или переподключения уведомлений не даёт, а возврат судьёй — одна строка «Судья вернул OG в базу», а не по строке на человека. Формулировка без рода: «<имя> теперь в <комната>».
- **Таймер.** `requestAnimationFrame` только рисует. Сигналы планируются на часах `AudioContext` и перепланируются при каждом снимке: в фоновой вкладке rAF не вызывается, а сигнал на 7:00 должен прозвучать. Сигналы задним числом не звучат: вошедший посреди речи не слышит уже прошедших.
- **Поправка часов:** несколько запросов времени при входе, медиана, периодическая пересверка.

### Ошибки и крайние случаи

- Браузер заблокировал автовоспроизведение (`AudioPlaybackStatusChanged`) — кнопка «Включить звук» (`startAudio()`).
- Ошибки устройств: `NotAllowedError` — как разрешить доступ; `NotReadableError` — камера или микрофон заняты другим приложением (например, Телемостом); `NotFoundError` — устройства нет. `devicechange` — переподхват устройства, например после смены наушников.
- Команды не проходят (бэкенд недоступен) — баннер «управление недоступно, звонок идёт».
- Плохая связь дольше ~10 с — подсказка «выключите камеру»; держателю флага — уже через 3–5 с.
- Сон дольше 10 минут — повторный вход по id и секрету (раздел 6).
- **Вторая вкладка:** BroadcastChannel и Web Locks. Новая вкладка спрашивает «перенести сюда?»; выбитая показывает «сессия перенесена» и `leave` не шлёт.
- **«Вы ещё здесь?»** Если я единственный подключённый участник раунда дольше 30 минут — вопрос; нет ответа 2 минуты — клиент закрывает свою сессию и показывает «вы вышли» с кнопкой «вернуться». Других людей это не касается.
- Неподдерживаемый браузер — отдельный экран со ссылкой «Открыть всё равно»: определение браузера — эвристика.
- Вышла новая версия — ненавязчивый баннер «обновите страницу между раундами»; `vite:preloadError` — предложение обновить.

### Страницы

Две, без перезагрузок, маршрутизация на React Router:
- `/` — стартовая страница: «Создать раунд» и недавние раунды этого браузера (из localStorage, где уже лежат id и секреты). Созданный раунд сразу открывается на `/r/:roundId`;
- `/r/:roundId` — экран перед входом (проверка устройств и доступности сервера, выбор камеры, имя, ссылка на раунд), затем раунд; микрофон при входе выключен. Полная проверка медиа — после подключения: для неё нужен токен.

### Отладочная панель

Только для чтения, по сочетанию клавиш, и в проде: состояние соединения, тип ICE-кандидата, подписки, версия снимка, последние ошибки. Проблемы будут на реальных сетях, а не в тестовой сборке.

### Производительность и доступность

- Селекторы Zustand на уровне плитки: снимок и смена говорящего не перерисовывают всё приложение.
- `livekit-client` — ленивым чанком на `/r/:roundId`. Бюджет начального JS — 150 КБ gzip; его проверяет CI, а локально — `pnpm build && pnpm budget`.
- Доступность: микрофон с клавиатуры; `aria-live` для «судья просит включить микрофон», «вас вернули в базу», «флаг свободен»; защищённое время и грейс не только цветом; `prefers-reduced-motion` для реакций; `axe` в одном E2E.

### Браузеры

Chrome, Edge и Яндекс Браузер — две последние версии; Safari 17 и новее; Firefox — последний; мобильные — по возможности. `build.target` в Vite — под эту матрицу.

### Прочее

- Стили — Tailwind 4; примитивы (слайдер громкости, меню, диалоги) — Radix через shadcn/ui, перестилизованные под визуальный язык [design.md](design.md): там же раскладка экрана раунда, безопасность действий и состояния.
- Интерфейс только на русском; строки в одном модуле, без фреймворка i18n. Коды ошибок домена переводятся в сообщения там же.
- Личные настройки (громкость каждого участника, «скрыть реакции», раскладка) — в localStorage; без хранилища приложение работает.
- TS strict и `noUncheckedIndexedAccess`; oxlint с проверками по типам; Prettier.

## 8. API

### Общие правила

- Всё под `/api`, на том же домене, что и SPA: Caddy отдаёт статику и проксирует API, CORS не нужен. Только HTTP/2.
- Стиль — команда на эндпоинт (`POST /drum/draw`), а не ресурсный REST: команды — глаголы домена. Чтение — `GET`.
- Команды раунда отвечают `200` с текущим снимком и требуют заголовок `Idempotency-Key` (UUID от клиента). Исключения:

  | Эндпоинт | Ответ | Ключ |
  |---|---|---|
  | `POST /api/rounds` | `{id}` | не нужен: повтор создаст лишний пустой раунд, лимит частоты по IP |
  | `POST /join` | ответ входа | не сохраняется: повтор даст лишний `pending`, который через 30 с считается отключённым, а через 5 минут выселяется |
  | `POST /messages` | сообщение | нужен (`ON CONFLICT`) |
  | `POST /leave`, `/reactions`, `/telemetry`, `/client-errors` | `204` | не нужен |

- Авторизация: `Authorization: Bearer <participant_id>.<secret>`. Сервер ищет хеш секрета по раунду и id и сравнивает за постоянное время. Повторный `join` передаёт id и секрет в теле.
- JSON в camelCase (в Python — snake_case через alias-генератор Pydantic). Время — целые миллисекунды эпохи.
- Ошибки — `{code, message}`:
  - `422` — схема запроса; тот же ключ идемпотентности с другим запросом;
  - `401` — неверные учётные данные;
  - `403` — `not_judge`;
  - `404` — нет раунда или участника;
  - `409` — нарушено правило домена: `judge_flag_taken`, `not_connected`, `drum_empty`, `round_full`, `entry_closed`;
  - `429` — лимит частоты;
  - `503` — `round_busy` (превышен `lock_timeout`), `updating` (идёт выкатка) или `round_unreadable` (неизвестная схема документа, раздел 5).
  - `recall` с базой — `422` по схеме: базы нет среди допустимых значений.
- Контракт: OpenAPI, включая снимок и конверт серверных пакетов `{topic: state | chat | chat_deleted | request_unmute | reaction, …}` (зарегистрирован в компонентах схемы). `just contract` пишет схему в `frontend/src/contract/openapi.json` и генерирует из неё TS-типы рядом. CI проверяет, что они не отстали, а `oasdiff` сравнивает схему PR со схемой базы и предупреждает о несовместимых изменениях для открытых старых вкладок.

### Эндпоинты

Пути раунда начинаются с `/api/rounds/{id}`.

| Метод и путь | Кто | Что |
|---|---|---|
| `POST /api/rounds` | стартовая страница | Создать раунд, вернуть id |
| `GET /api/time` | любой | Серверное время для поправки часов |
| `POST /join` | любой | Войти: имя, при повторном входе — id и секрет. Ответ: id и секрет (секрет — только при первом входе), URL LiveKit, токен, снимок, версия приложения |
| `POST /leave` | браузер при закрытии вкладки | С `sid` своей сессии; через `fetch` с `keepalive`: в отличие от `sendBeacon`, он отправляет заголовок авторизации |
| `GET /snapshot?epoch=&since=` | участник | Снимок; `304`, если совпадают epoch и версия. Раз в 15 с и после переподключения |
| `GET /messages?before=&after=&limit=` | участник | История чата: последние 50, листание назад, догрузка вперёд |
| `POST /messages` | участник | Написать в чат |
| `POST /reactions` | участник | Реакция участникам своей комнаты |
| `POST /enter` | участник | Перейти в комнату |
| `POST /hands/raise`, `/hands/lower` | участник | Своя рука |
| `POST /judge/claim` | участник | Взять флаг |
| `POST /judge/release`, `/judge/hand-over` | судья | Отдать или передать флаг |
| `POST /timers/{prep\|speech}/start\|pause\|reset\|set\|configure` | судья | Таймеры и их длительность |
| `POST /speech/next`, `/speech/undo` | судья | «Следующая речь» и её отмена |
| `POST /motion` | судья | Резолюция и инфослайд; пустой текст убирает резолюцию |
| `POST /drum/draw\|reset\|configure` | судья | Барабан |
| `POST /recall`, `/recall-all` | судья | Вернуть в базу подкомнату или всех |
| `POST /hands/lower-of`, `/hands/lower-all` | судья | Чужие руки |
| `POST /mute`, `/request-unmute` | судья | Микрофоны |
| `POST /telemetry` | участник | Выжимка `getStats()` и метрики SLO пачками |
| `POST /client-errors` | участник | Ошибки фронтенда вместо стороннего трекера |

Служебные: `POST /internal/livekit/webhook` — Caddy его не проксирует, защита — непубликуемый путь и проверка подписи; `GET /api/health` — для агента выкатки и Caddy, без зависимости от LiveKit. Служебные команды администратора — CLI на сервере, не HTTP.

### Снимок

`RoundSnapshot` один и тот же в ответах команд, `GET`, data-пакетах и метаданных:
- `epoch`, версия, `committedAt` (серверное время коммита — для замера доставки), версия приложения;
- участники в агрегате (не больше 40): id, имя, комната, присутствие, время подъёма руки;
- вход открыт или закрыт;
- флаг: держатель; последний держатель с именем, причина и время освобождения;
- таймеры: для каждого — длительность, статус, момент окончания или остаток; номер речи и доступна ли отмена «Следующей речи»;
- резолюция и инфослайд;
- барабан: включённые позиции, выпавшие, режим, последний результат.

Секретов в снимке нет. Номер руки в очереди не передаётся — клиент считает его сам по времени подъёма и комнате.

### Лимиты

| Что | Значение |
|---|---|
| Создание раунда | 10 в час на IP |
| Вход новых участников | 60 в минуту на IP (клуб за одним NAT); повторный вход по id и секрету не ограничивается |
| Команды | 10 в секунду на участника |
| Чат | 5 сообщений за 10 с на участника |
| Реакции | 5 в секунду на участника, в памяти процесса |
| Длины | имя 1–40 символов (≤ 80 байт UTF-8), резолюция до 300 (≤ 600 байт), инфослайд до 1500 (≤ 3000 байт), сообщение до 1000 символов |
| История чата | страница — 50 сообщений |
| Токен LiveKit | 10 минут |

Лимиты считаются в Postgres (`rate_limits`, фиксированное окно, `INSERT … ON CONFLICT DO UPDATE … RETURNING`). IP клиента берётся из `X-Forwarded-For` только от Caddy (`--proxy-headers`, `--forwarded-allow-ips` у uvicorn); заголовок от клиента не доверяется.

### Прочее

- В пути нет версии API: SPA и бэкенд выкатываются вместе, совместимость держит контракт в CI.
- Если версия приложения в снимке новее, чем у открытой вкладки, клиент показывает «Вышла новая версия — обновите страницу между раундами». Сигнал, а не принудительная перезагрузка.

## 9. Тесты

### Принцип

Больше всего тестов там, где правила и главный риск, а не там, где проще писать. Правила — домен раунда; главный риск — подписки на клиенте (звук подготовки в базе). Домен и исправления багов — по TDD: сначала тест, который воспроизводит правило или баг, потом код.

### Бэкенд

| Слой | Как | Что проверяем |
|---|---|---|
| Домен | Чистые синхронные тесты; время и случайность — аргументами; агрегаты собираются тестовыми билдерами (`a_round().with_judge(...)`) | Каждый из 14 инвариантов и каждая строка таблицы переходов присутствия — хотя бы один тест |
| Домен, свойства | Stateful-тесты Hypothesis: случайные последовательности команд, вебхуков и сверок от случайных участников | После любой последовательности: держатель флага подключён; каждый участник ровно в одной комнате; `recall` опустошает подкомнату; `undo_next_speech` точно возвращает таймер и номер; версия растёт; в режиме `remove_drawn` нет дублей; маппер туда-обратно без потерь; снимок не больше 14 КиБ |
| Маппер и схема | Туда-обратно домен ↔ JSON; документ-фикстура на каждую версию схемы | Ничего не теряется; код N читает документы N+1; неизвестная схема — ошибка, а не сброс |
| Сценарии | Порты — фейки в памяти: репозиторий, часы, случайность, outbox, Медиа | События; outbox пишется в транзакции; идемпотентность |
| Postgres | Настоящий Postgres (в CI — service-контейнер) | `FOR UPDATE`; параллельные `claim_judge` — ровно один победитель; одновременные запросы с одним ключом — одно выполнение; `lock_timeout` → `503` |
| API | FastAPI через httpx на настоящем Postgres, Медиа — фейк | Авторизация; перевод ошибок домена в коды; исключения из правила ключей; лимиты частоты, в том числе IP за прокси |
| Медиа | Настоящий LiveKit из `compose.yaml`, боты на Python SDK | Создание медиакомнаты; снимок в пакете и метаданных; подписанные вебхуки; `ListParticipants`; мут; бот с попыткой отправить data-пакет — не доходит; лидер-публикатор падает посреди выгрузки, работают несколько процессов, медиакомната пересоздаётся. Дубли, пропуски и перестановки вебхуков — поддельными запросами |
| Контракт | Генерация OpenAPI → TS, `oasdiff` | Типы фронтенда не отстали; несовместимые изменения видны |
| Архитектура | `import-linter` | Слои и направление зависимостей |

### Фронтенд

| Слой | Как | Что проверяем |
|---|---|---|
| Домен | Vitest, таблицы случаев и fast-check | Таймер с поправкой часов при разных длительностях, защищённое время, сигналы, очередь рук по комнате. Главное свойство: при любом снимке функция желаемых подписок не подписывает на звук того, кто не в моей комнате |
| Сценарии и стор | Фейковый порт `MediaSession`, фейковые часы `AudioContext` | Побеждает наибольшая пара (epoch, version) при пакетах не по порядку; порядок операций при переходе; шаг от устаревшей версии отменяется; повтор команды после таймаута не дублируется; сигналы звучат в фоновой вкладке; повторный вход после истёкшего токена и исключения из него; «Вы ещё здесь?» на фейковых часах — 30 минут одному → вопрос, 2 минуты без ответа → сессия закрыта, повторного входа нет |
| Компоненты | Testing Library, точечно | Панель судьи есть только у судьи; баннер «флаг свободен» и кнопка «взять снова»; баннер «управление недоступно» |
| Архитектура | `dependency-cruiser` | Слои |

### E2E

Playwright, Chromium с поддельными камерой и микрофоном, против полного стека в CI: Postgres и LiveKit из `compose.yaml` (не `services:` GitHub Actions — они стартуют до checkout и не видят конфиг), бэкенд, собранный фронтенд.

Сценарии: три браузера входят, один берёт флаг; двое уходят в OG — изоляция звука; `recall` возвращает их в базу; таймер виден во всех комнатах; жеребьёвка даёт системную строку в чате; после перезагрузки — та же комната; вторая вкладка — вопрос «перенести сюда?»; `axe` на экране раунда.

Изоляция звука проверяется на той же сборке, что уходит в прод, без отладочных хуков: `RTCPeerConnection` перехватывается через `addInitScript`, у каждого браузера свой тон (`--use-file-for-fake-audio-capture`), на выходе `AnalyserNode` определяет, чьи тоны слышны.

Браузеры: в CI — Chromium; Firefox — если поддельные устройства заведутся стабильно. Safari и Яндекс Браузер — вручную: WebKit в Playwright не настоящий Safari, а подводные камни из ресерча — именно в Safari. На Mac их проверяют локально с первого среза: `localhost` — безопасный источник. iOS Safari и телефоны — на стенде, в срезе С.

### Агент выкатки

Тесты против поддельного реестра и поддельного compose: неудачный релиз запоминается и не повторяется; откат возвращает образы и статику; упавшие миграции роняют релиз. Пропуск миграций, когда база впереди образа, решает сам `debatemeet.migrate` — это проверяют его тесты против Postgres. Тесты агента — `deploy/server/tests/`, stdlib `unittest`, как у git-хуков. CI гоняет их в задаче `Images` вместе с ruff и mypy агента из `uv.lock` бэкенда, локально — `just test` и `just lint`.

### Стенд — не CI

- Дымовые проверки — автоматически при каждой выкатке (раздел 10).
- Перед первой игрой и крупными релизами — нагрузка и сеть: `lk load-test` на 30 участников и 11 камер; свои боты меряют время перехода (звук ≤ 1 с, видео ≤ 2 с); потери 10% через `tc netem` — разборчивость звука; только TURN/TLS; проверки из ресерча и раздела 6. Скрипты — в `tools/`, запускаются вручную: они долгие и зависят от сети.

### Покрытие

Общего порога нет — он приводит к тестам ради цифры. Вместо него: у каждого инварианта, каждого перехода присутствия и каждой команды есть тест; ветки домена покрыты полностью на обеих сторонах — домен чистый, и порог там дёшев.

## 10. CI/CD

### Исходные условия

- **Репозиторий публичный.** Actions бесплатны без лимита минут. PR из форков не видят секретов, а секретов в GitHub — минимум.
- **Серверы в Москве.** Соединения из РФ к зарубежным адресам режутся, в июне 2026 у Selectel сбоили HTTPS и SSH. Серверы не ходят за границу (за образами, STUN, трекером ошибок), GitHub не ходит на серверы. Единственное исключение — ACME у Caddy: удостоверяющие центры, которым доверяют браузеры, находятся за границей.
- **Звонки нельзя рвать.** Бэкенд без состояния; перезапуск LiveKit и Caddy обрывает соединения.

### Окружения

- **Стенд** — отдельный сервер Selectel меньше прода, с той же конфигурацией сервисов (compose, LiveKit, Caddy, Postgres), своими доменами и ключами. Конфигурации стенда и прода записаны в [спеке](spec.md), раздел «Сервер и эксплуатация». Каждый мёрж в `main` сначала попадает сюда. Здесь же гоняются проверки до первой игры, еженедельная проверка восстановления бэкапа, и стенд служит тёплым резервом, если прод потерян. На нагрузочные тесты и на время резерва его поднимают до размера прода.
- **Прод** получает релиз только после того, как стенд его принял.
- Стенд на том же сервере, что и прод, делил бы с ним канал и процессор во время раундов и требовал бы второй LiveKit со своими портами и доменом TURN.

### CI: проверки на каждый PR и на `main`

- Задачи параллельно:
  - **бэкенд:** ruff, mypy, `import-linter`, pytest на Postgres в service-контейнере;
  - **Медиа:** тесты против LiveKit — отдельная задача с `docker compose up -d livekit`;
  - **фронтенд:** oxlint, Prettier, `tsc`, Vitest, `dependency-cruiser`, сборка, бюджет начального JS;
  - **контракт:** генерация OpenAPI → TS-типы и `git diff --exit-code`, `oasdiff`;
  - **образы:** сборка `backend`, `web` и `bundle` с кэшем слоёв, hadolint и shellcheck. Бэкенд стартует против Postgres, становится healthy, отдаёт версию сборки и работает не от root. В `web` лежит `index.html` со всеми файлами, которые он просит. Бандл принимают `docker compose config`, `caddy adapt --validate` и LiveKit — у последнего `ports` выходит с кодом 0 даже на неразобранном конфиге, поэтому смотрится его вывод;
  - **E2E** на Playwright против стека из `compose.yaml` — когда появятся сценарии (раздел 9);
  - **гигиена:** CodeQL, `zizmor` для воркфлоу, проверка заголовка PR по формату коммитов (при squash-merge сообщение коммита — это заголовок PR, хук его не видит).
- Проверяется только затронутое. Сводная проверка одна — итоговая задача `ci-ok`, которая собирает результаты остальных; она падает, если упала сама задача фильтра путей. Обязательной в GitHub она не сделана — защиты ветки нет по решению автора: PR сливают только при зелёном последнем `ci-ok` на вершине PR. Изменения в `.github/`, lock-файлах и контракте запускают всё. Гигиена и CodeQL идут на каждом PR целиком: они дешёвые, а сканированию кода нужен анализ каждого языка для сравнения с базой. Переименование PR перезапускает CI: заголовок станет сообщением коммита.
- Кэш uv, pnpm, браузеров Playwright и слоёв Docker (`type=gha`); новый пуш в тот же PR отменяет предыдущий прогон.
- Цепочка поставок: `permissions: contents: read` по умолчанию; actions закреплены по SHA коммита; никакого `pull_request_target`.
- Dependabot (`.github/dependabot.yml`) раз в неделю обновляет actions, pnpm, uv и образы `compose.yaml`.
  - Версия попадает в PR не раньше чем через 7 дней после выхода: взломанный или сломанный релиз к этому времени обычно отзывают. Обновления безопасности — без задержки.
  - Мелкие обновления собираются в один PR на экосистему.
  - Digest образов внутри воркфлоу (Postgres для тестов, oasdiff, hadolint, shellcheck, Caddy и LiveKit для проверки бандла) Dependabot не видит: их обновляют руками, Caddy и LiveKit — вместе с `deploy/server/compose.yaml`.
  - Закреплённые линии Dependabot не сдвигает: TypeScript остаётся на 6.0, `@types/node` — на мажоре Node, на котором всё работает, а `uv_build` меняется руками вместе с самим uv.
- Модель веток — trunk-based: короткие ветки, PR в `main` с `ci-ok`, squash-merge.

### Сборка

- CI собирает образы `backend`, `web` (статика SPA) и `bundle` и пушит в Selectel Container Registry — внутри РФ, в том же облаке, что и серверы. Пока реестра нет, задача `Images` только собирает и проверяет. Теги: `sha-<коммит>` и `stage`; выкатка всегда идёт по digest (`@sha256:…`), а не по тегу.
- **Релиз — это digest образа `bundle`.** Метки бандла `debatemeet.backend-image` и `debatemeet.web-image` закрепляют образы релиза по digest, поэтому CI собирает бандл последним, после пуша `backend` и `web`. Тег `stage` двигается один, на бандле: агент не увидит наполовину собранный релиз, а «проверенный digest» для прода — тоже один.
- Сторонние образы (Postgres, LiveKit, Caddy) CI перекладывает в этот реестр; в бандле развёртывания они указаны по digest. Серверы за образами за границу не ходят. Перекладка сохраняет digest: `docker buildx imagetools create --tag <реестр>/mirror/<образ> <оригинал>@sha256:…` копирует манифест как есть — проверено на локальном реестре.
- Образ бэкенда (`backend/Dockerfile`) — многоэтапная сборка на `python:3.14-slim`: сначала слой зависимостей, потом слой кода. Обычная выкатка тянет только слой кода: он весит сотни килобайт, а зависимости — больше сотни мегабайт. Пользователь без root, код принадлежит root и только читается, байткод скомпилирован заранее. `HEALTHCHECK` опрашивает `/api/health`, а тот проверяет и базу: по нему агент ждёт бэкенд после выкатки.
- Образ `web` (`frontend/Dockerfile`) — только собранная статика в `/web`, на `scratch`: запускать в нём нечего, агент копирует файлы в папку статики. Tailwind ищет классы только в `src/`, поэтому образ, CI и локальная сборка дают один и тот же бандл.
- Базовые образы закреплены по digest, их обновляет Dependabot: Python остаётся на 3.14, Node — на 24, а uv в образе меняется руками вместе с версией в CI. Локально оба образа собирает `just images`.
- Конфигурация развёртывания (compose, Caddyfile, конфиг LiveKit без ключей) приезжает тем же путём, отдельным образом-бандлом; `git pull` с GitHub на серверах нет. Файлы лежат в `deploy/server/`, образ `bundle` — на `scratch`, с файлами в `/bundle`. Стенд и прод различаются только `.env` сервера по образцу `env.example`. Конфиги Caddy и LiveKit лежат в каталогах `caddy/` и `livekit/` и монтируются каталогами: смонтированный файл держит inode, с которым создан контейнер, и файл, заменённый агентом, контейнер бы не увидел. В бандле же агент выкатки и его юниты systemd.
- Сеть на сервере. LiveKit, Caddy и бэкенд работают в host-сети и говорят через `127.0.0.1`:
  - Caddy проксирует к бэкенду и LiveKit;
  - LiveKit шлёт вебхуки бэкенду;
  - бэкенд вызывает LiveKit.

  Бэкенд видит Caddy как `127.0.0.1` — ровно тот адрес, от которого uvicorn по умолчанию принимает `X-Forwarded-For`. Бэкенд слушает только loopback. Postgres — в сети bridge и публикует 5432 на `127.0.0.1`. Имя проекта compose — `debatemeet-server`: с именем `debatemeet` dev-стека он забрал бы на машине разработчика его контейнеры и том Postgres.
- Сторонние образы в compose указаны как `${DM_REGISTRY}/mirror/…` с digest оригиналов. За переменной Dependabot их не видит: их обновляют руками, как digest в `ci.yml`.
- Токены реестра раздельные: у CI — только на пуш, у серверов — только на чтение.
- Версия приложения — дата коммита по UTC и его короткий sha, например `2026.09.28-08f224af01ba`; сборка с незакоммиченными правками получает `-dirty`. Версию считает `tools/app-version.sh`. В образ она попадает аргументом сборки `APP_VERSION`: в бэкенде это `DM_APP_VERSION`, у обоих образов — метка `org.opencontainers.image.version`. Заметки о том, что нового, пишутся руками.
- Подпись образов (cosign) и SBOM — в срезе 7: проверка без ключа требует Sigstore за границей, поэтому подпись будет ключом, без загрузки в журнал прозрачности.

### Выкатка

```
PR → ci-ok → squash-merge в main
→ CI: образы в реестр, тег stage (релизный workflow с concurrency — sha выкатываются по порядку)
→ агент стенда забирает stage: миграции, выкатка, дымовые проверки → «проверенный digest»
→ агент прода спрашивает у стенда проверенный digest (РФ → РФ, одно облако)
→ забирает его, когда в раундах пусто и заморозка не включена
```

**Агент** — одинаковый на стенде и проде, systemd-таймер раз в минуту, под `flock`:

```
новый digest (на стенде — тег stage, на проде — проверенный digest стенда)?   нет → выход
этот digest уже падал?                               да → выход (алерт уже был)
в медиакомнатах кто-то есть (ListParticipants)?      да → выход, попробуем через минуту
режим обновления → join отвечает 503 updating → проверить пустоту ещё раз
pg_dump → объектное хранилище
python -m debatemeet.migrate одноразовым контейнером нового образа   не 0 → digest упал
                                                     (база впереди образа — он сам пропускает)
новая статика → в общую папку assets, новый index.html рядом
пересоздать backend, дождаться health-check
  не поднялся → вернуть прежние образы и index.html, digest отметить упавшим, алерт
переключить index.html; выйти из режима обновления
на стенде — дымовые проверки → «проверенный digest»
аннотация в Grafana, сообщение в Telegram
```

- **Pull, а не push по SSH.** Входящие соединения из-за границы — ровно то, что сбоило в июне 2026. Ключа от серверов в GitHub нет. Проверка «в раундах пусто» живёт рядом с LiveKit.
- **«Вне раундов» работает само.** Мёрж во время игры никого не дёргает: агент дождётся, пока все разойдутся. Забытые вкладки закрываются сами («Вы ещё здесь?», раздел 7); если релиз ждёт дольше суток — алерт и ручная команда принудительной выкатки.
- **Заморозка** — тег в реестре, ставится и снимается ручным workflow: пока он есть, агент прода не выкатывает (например, перед турниром).
- **Дымовые проверки на стенде:** health, создать раунд, войти ботом, подключиться к медиакомнате, снимок выгружен в метаданные, снаружи открыты только нужные порты.
- **Бэкенд перезапускается мягко.** uvicorn дорабатывает начатые запросы. `lb_try_duration` у Caddy повторяет только несостоявшиеся соединения: уже отправленный POST, если оборвался, клиент повторяет с тем же ключом идемпотентности.
- **Статика.** Хешированные файлы копятся в общей папке `assets` и чистятся через 30 дней: у открывших старую версию догружаются её чанки. `index.html` отдаётся без кэша. Caddy отдаёт `/assets/*` из `assets/` с `immutable`, а всё остальное — из `current/`, где лежит `index.html` текущего релиза. Монтируется родительская папка (`DM_WEB_ROOT`, только чтение), `current` — относительный симлинк на папку релиза, переключение — `mv -T`: Docker разворачивает симлинк при создании контейнера, и смонтированный напрямую симлинк навсегда остался бы на старой папке.
- **Миграции** совместимы с предыдущей версией кода (expand → contract) — и для таблиц, и для JSONB-документа (раздел 5). Откат кода не требует отката схемы, схему никогда не откатываем. Перед каждой миграцией — дамп базы.
- **Откат.** Автоматический — если не прошёл health-check. Ручной — workflow ставит прежний digest, агент забирает его как обычный релиз.
- **LiveKit и Caddy** обновляются тем же путём и по тому же правилу «в раундах пусто»; конфиг Caddy применяется через `caddy reload`. Не задевает ли `reload` TURN/TLS — проверить на стенде. Мажорные обновления Postgres — руками.

Проверить до реализации: пуш из раннеров GitHub в реестр Selectel проходит стабильно; серверы тянут из реестра внутри облака без ограничений.

**Тонкий агент стенда** (срез 0б) — `deploy/server/agent.py`: stdlib Python 3.9+ на системном интерпретаторе сервера, приезжает в бандле. Таймер `debatemeet-agent.timer` запускает `agent.py tick` через минуту после окончания прошлого прогона, `flock` держит сам агент. Кроме `tick` есть `status` и `compose …` — docker compose с env-файлами релиза.
- **Чего в нём нет** по сравнению с полным: проверки пустоты медиакомнат, режима обновления, дампа перед миграцией, дымовых проверок и аннотаций. Поэтому он может перезапустить LiveKit или перечитать Caddy посреди раунда. Для стенда до первых живых игр это допустимо.
- **Раскладка** в `/srv/debatemeet`:
  - `server/` — проект compose: файлы бандла текущего релиза, `.env` оператора и `release.env`, куда агент пишет образ бэкенда;
  - `web/` — `DM_WEB_ROOT`: `assets/`, `releases/<id>/index.html` и `current`;
  - `releases/<id>/` — бандл, файлы web и `release.json` недавних релизов, для отката;
  - `state.json` — текущий и прежний релиз и упавшие.
- **Шаги.**
  1. Digest тега `stage`; тот же, что текущий, или уже падавший — выход без записи в журнал.
  2. `pull` бандла, метки, распаковка бандла и web.
  3. Статика — в `assets` и `releases/<id>/`, но `current` ещё прежний.
  4. Файлы бандла — в `server/`: каталоги синхронизируются пофайлово. `release.env` получает новый бэкенд.
  5. `compose up -d --wait postgres`, затем `compose run` с `python -m debatemeet.migrate`.
  6. `compose up -d --wait`: бэкенд должен стать healthy.
  7. Изменился `caddy/` — `caddy reload`; изменился `livekit/` — перезапуск LiveKit. На первом релизе контейнеры и так стартуют с новыми файлами.
  8. Переключение `current`, `state.json`, уборка.
- **Сбой** на миграциях, сервисах или конфигах. Сначала релиз отмечается упавшим — если агент умрёт посреди отката, он не станет повторять этот релиз. Затем откат: файлы и `release.env` прежнего релиза, `compose up`, и заново `reload` или перезапуск того, что успело примениться. Статика не переключалась, откатывать её не нужно. Первому релизу откатываться не к чему.
- **Реестр или Docker не отвечают** — прогон падает, но релиз не винится, и через минуту агент попробует снова. Бандл без меток образов — сломанный релиз.
- **Уборка.** Остаются текущий, прежний и ещё пять последних релизов. Из `assets` уходят файлы старше 30 дней, которых нет ни в одном оставленном релизе. Файлы каждого нового релиза при выкатке получают свежее время.
- **Первая установка:**
  1. `.env` по `env.example`;
  2. `docker login` в реестр токеном только на чтение;
  3. файлы бандла `stage` — в `server/` (`docker create` и `docker cp`);
  4. `systemctl link` обоих юнитов и `systemctl enable --now debatemeet-agent.timer`.

  Первый прогон выкатит `stage` сам.
- **Проверено.**
  - Юнит-тесты с поддельными реестром и compose (раздел 9).
  - Прогон с настоящими Docker и compose против локального реестра:
    - первый релиз — миграции, SPA, API и LiveKit через Caddy;
    - новый бэкенд с новым Caddyfile — `caddy reload` без пересоздания контейнера;
    - бэкенд с падающей проверкой здоровья — откат за 15 с, релиз помнится упавшим.

### Эксплуатация

- **Бэкапы.** Ежедневный зашифрованный `pg_dump` (systemd-таймер) в объектное хранилище, глубина — 14 дней, плюс дамп перед каждой миграцией. Раз в неделю автоматическое восстановление на стенде с проверочным запросом; метрика «возраст последнего проверенного бэкапа». Потеря данных при аварии — не больше суток. Восстановление меняет `epoch` (раздел 5). Ключ шифрования бэкапов и `.env` серверов — в менеджере паролей, иначе восстановление не состоится.
- **Диск.** Ротация логов Docker (`max-size` 20 МБ, `max-file` 5 у каждого контейнера — в compose сервера), `docker image prune` в агенте, чистка старой статики, срок хранения Prometheus, алерт на заполнение 80%.
- **Периметр.** Наружу открыты только 80/443 TCP, 7881 TCP и 7882 UDP. Контейнеры публикуют порты только на `127.0.0.1`: Docker открывает опубликованные порты в обход ufw. Сервисы в host-сети слушают loopback сами; исключение — порт TURN 5349, его держит закрытым ufw. Порт-скан снаружи — в дымовых проверках стенда.
- **Домены и TLS.** Регистратор и DNS — российские; TTL A-записей — 300 с. Сертификаты продлеваются за 30 дней до истечения; проба сроков с алертом за 21 день; если ACME по HTTP-01 не проходит — запасной путь DNS-01.
- **Внешнее наблюдение.** Стенд и прод проверяют друг друга: `/api/health`, TCP до TURN/TLS, WSS LiveKit, сроки сертификатов. Если пропал сигнал-пульс, тоже приходит алерт. Алерты — в Telegram и запасным каналом на почту через российский SMTP. В текстах алертов нет имён и id.
- **Алерты под реальный объём.** Во время активного раунда — только симптомы: массово плохое качество связи, ошибки команд, отставание доставки снимка (`version − data_version`), сбои вебхуков. Вне раундов — ежедневная сводка: диск, бэкап, сертификаты, одинаковы ли версии на стенде и проде. Алертов на процессор нет. Перед игрой — команда `just preflight`.
- **Ранбуки** в `docs/runbooks/`, формат «симптом → проверка → действие»: LiveKit лёг; кончился диск; сертификат не продлился; режут UDP; сервер недоступен; восстановление из бэкапа; утечка ссылки или тролль (служебные команды); удаление данных по просьбе; ротация секретов. Каждый прогоняется на стенде хотя бы раз.
- **Аварийное восстановление.** Стенд — тёплый резерв: последний бэкап восстанавливается на стенд, A-записи переключаются, клубам сообщается.
- **Трафик.** Панель и алерт на 70% включённых 3 ТБ в месяц; у Selectel уточнить, считаются ли 3 ТБ на сервер или на проект.
- **Ошибки фронтенда** — в свой `/client-errors`, в таблицу телеметрии; source maps остаются на сервере. Sentry SaaS не используем: он за границей и вывозит данные.
- **Логи** — structlog в JSON с `request_id`, `client_session_id` клиента и `sid` LiveKit; id раунда — хеш-префиксом, access-логи Caddy и uvicorn маскируют путь раунда.
- **Служебные команды** администратора — `just admin …` на сервере (раздел 3).
- **Секреты.** `.env` на серверах. В GitHub — только токен реестра на пуш; он доступен workflow на любой ветке — это принятый риск одиночного репозитория. Ключи LiveKit ротируются через несколько ключей в конфиге.

### Локальные проверки и Claude

- **lefthook, `pre-commit`:** ruff и oxlint с Prettier на изменённых файлах.
- **lefthook, `commit-msg`:** `tools/git/check_message.py` — одна строка `type: description` на английском, типы `feat|fix|refactor|docs|test|chore`, без тела, без трейлеров и подписей Claude. Тот же скрипт в CI проверяет заголовок PR.
- **Claude-хук** `.claude/hooks/git-guard.py`. Claude может коммитить, пушить feature-ветки, открывать и обновлять PR и сливать свои PR. Запрещено: пуш в `main`, force-push, `--no-verify`, `--amend`, подмена `hooksPath`, массовый `git add` (`.`, `-A`, `-u`), релизы, операции с репозиторием, ручной запуск workflow.
- **Слияние.** Хук пускает только `gh pr merge N --squash` и перед этим спрашивает GitHub через `gh pr view`, а если ответа нет — отклоняет. Условия:
  - PR из этого репозитория, база — `main`: слияние в другую ветку и сломало стек среза 0а;
  - PR открыл человек, а не бот вроде Dependabot;
  - PR не меняет ограничители Claude (`.claude/`, `tools/git/`, `lefthook.yml`) — такие сливает автор;
  - последний запуск `ci-ok` на вершине PR зелёный. Считается только последний: правка PR перезапускает CI на той же вершине, и прерванный ранний запуск остаётся в списке проверок.

  `--admin`, `--auto`, `--merge`, `--rebase`, `--delete-branch` и `--repo` отклоняются. Текст коммита и PR с атрибуцией (`Co-Authored-By`, «Generated with», Claude как автор, 🤖) хук отклоняет — имя файла `CLAUDE.md` атрибуцией не считается; заголовок PR проверяет по правилам `commit-msg`. Хуки — stdlib Python 3.9+, чтобы работать на системном интерпретаторе; тесты — `tools/git/test_*.py`.
- Хук — страховка от случайностей, а не граница безопасности: его можно обойти. По решению автора этого достаточно; защита ветки в GitHub и отдельный токен для Claude не настраиваются.
- Коммиты и PR — только от имени автора: git-идентичность репозитория и его учётная запись `gh`. Свои PR Claude сливает сам по правилам выше; остальные сливает автор.

## 11. Дорожная карта

### Планка качества: хайтир пет-проект уровня препродакт

Бо́льшая часть заложена в разделах выше: DDD и гексагон, правила слоёв с проверкой в CI, stateful-тесты, стенд, CD без обрыва звонков, эксплуатация под сеть РФ. Сверх этого:
- **Решения документируются дальше.** Этот документ — снимок на 28 сентября 2026. Каждое следующее крупное изменение — ADR в `docs/adr/`: контекст, решение, альтернативы, последствия.
- **SLO из нефункциональных требований.** Показатели (SLI), их считает клиент и шлёт телеметрией:

  | SLI | Цель |
  |---|---|
  | `join_to_first_audio_ms` — от «Войти» до первого удалённого звука (или до `connected`, если в комнате пусто) | ≤ 5 с у 95% входов |
  | `room_switch_audio_ms` — от `enter` до звука новой комнаты | p95 ≤ 1 с |
  | `snapshot_delivery_ms` — от `committedAt` до применения на клиенте с поправкой часов | p95 ≤ 500 мс |
  | `clock_offset_uncertainty_ms` — половина RTT лучшего замера времени | ≤ 250 мс |
  | `reconnect_ms` — от обрыва до восстановления | ≤ 10 с |
  | Доля участнико-минут с качеством связи «хорошо» и выше | ≥ 90% |

  Плюс звуковые RTT и джиттер из `getStats`, причина ограничения качества (процессор или сеть) и доля TURN-кандидатов — ранний сигнал, что UDP начали резать. Окно — 28 дней; после каждой игры — отчёт «SLO этого вечера»; вечер с нарушением — следующий срез начинается с починки. Сырая телеметрия — в Postgres на 30 дней; агрегаты — в `/metrics` без меток раунда и участника. Дашборды и алерты — кодом в репозитории.
- **Релизы:** версия — дата и sha, та же версия уходит в снимок (баннер «обновите страницу»); заметки о новом — руками.
- **Цепочка поставок:** выкатка по digest, раздельные токены реестра; подпись образов и SBOM — в срезе 7.
- **Витрина репозитория:** README (что это, схема архитектуры, запуск одной командой, ссылки на документы), `SECURITY.md`. Лицензии пока нет — все права защищены. Код из La Suite Meet (MIT) и LiveKit Meet (Apache-2.0), если его берём, — с сохранением их уведомлений.
- **Продуктовая сторона:** метрики продукта — из журнала, без сторонних трекеров: раунды в неделю, участники, длительность, как пользуются барабаном и таймерами. Кнопка «сообщить о проблеме» прикладывает последнюю телеметрию связи и кольцевой буфер клиентских логов.

### Срезы

Каждый срез заканчивается тем, что можно потрогать: до среза С — локально на dev-стеке, ботами и в E2E в CI, после — на стенде. Порядок — по риску: самое опасное раньше. Исключение — стенд: его риски касаются в основном конфигурации развёртывания, а не кода, и он идёт после среза 6 ([ADR 0001](adr/0001-stand-after-slice-6.md)).

- **0а. Репозиторий и локальная среда.** Структура пакетов по разделам 4 и 7; правила слоёв в CI; хуки; `CLAUDE.md`; `justfile` (`setup`, `dev`, `test`, `lint`, `contract`, `bots`); `compose.yaml` с вебхуками LiveKit, `auto_create: false` и `max_participants`; генерация контракта; CI с `ci-ok`, CodeQL, `zizmor`, проверкой заголовка PR; README; шаблон ADR; заготовка ботов `just bots N`: в 0а бот сам создаёт медиакомнату серверным API, входит с dev-токеном, публикует тон и тестовую картинку; вход через `join` — в срезе 1, сценарий переходов — в срезе 2. Из шаблона Vite убрать `@livekit/components-react` и `@livekit/components-styles`. Телефоны в разработке — только через стенд.
- **0б. Стенд без ресурсов.** Образы `backend`, `web` и `bundle`, их сборка и проверка в CI, бандл развёртывания с ротацией логов, вход миграций и тонкий агент. Тонкий агент — это агент из раздела 10 без проверки пустоты медиакомнат, режима обновления, дампа перед миграцией, дымовых проверок и аннотаций: digest берётся из тега `stage`; статика, бандл, откат и память об упавших digest — как в разделе 10; тесты агента из раздела 9 — в этом срезе. Всё, что требует ресурсов, — в срезе С.
- **1. «Вошёл по ссылке и слышу базу».** Стартовая страница с недавними раундами; `create_round`; экран перед входом с проверкой устройств и понятными ошибками; экран неподдерживаемого браузера; `join`; медиакомната и токен; присутствие по таблице переходов со сверкой; снимок по обоим каналам, лидер-публикатор, проверка устарелости. Первым делом — проверка эха с `webAudioMix` в Chrome на динамиках ноутбука, вместе со звуковыми сигналами таймера: от неё зависит громкость до 200%.
- **2. Комнаты — главный риск.** Менеджер подписок; `enter`; карта комнат; `recall`; флаг судьи с кнопкой «взять снова»; вторая вкладка; «Вы ещё здесь?»; служебные команды: освободить флаг, убрать участника, закрыть вход. E2E на изоляцию звука. Время перехода мерится локально, с задержкой и потерями через `tc netem` в контейнере LiveKit; на настоящей сети — в срезе С.
- **3. Время.** Поправка часов, таймеры с настраиваемой длительностью, защищённое время, сигналы на часах `AudioContext`, «Следующая речь» с отменой.
- **4. Резолюция, барабан, чат** — с историей, системными строками через outbox, удалением сообщений администратором.
- **5. Руки, микрофоны, реакции через бэкенд, громкость каждого участника.**
- **6. Устойчивость и связь.** Индикаторы качества, подсказка «выключите камеру», понятные сообщения при неудаче подключения (белые списки), повторный вход после сна, телеметрия и SLI, кнопка «сообщить о проблеме», отладочная панель, баннер новой версии. Плохая сеть и блокировки портов имитируются локально; настройка под настоящую сеть — в срезе С.
- **С. Стенд.** Сначала — прогон бандла и агента локально, чтобы поймать расхождения, накопившиеся за срезы 1–6. Потом реестр и токены, релизный workflow, зеркала сторонних образов, сервер, домены, периметр, ежедневные бэкапы, алерты агента. Срез закрыт, когда слияние в `main` само доезжает до стенда. На стенде — всё, что локально не проверить: ACME, настоящая host-сеть и ufw, порт-скан снаружи, откат агента, телефоны и iOS Safari, прогон только через TURN/TLS, время перехода на настоящей сети, проверки раздела 6. Нужно от автора: сервер Selectel для стенда; домены приложения, LiveKit и TURN для стенда и прода у российского регистратора; Container Registry и объектное хранилище Selectel; бот Telegram и почта для алертов.
- **7. Прод.** Сервер прода, TURN/TLS на 443, алерты, перекрёстное наблюдение, бэкапы с проверкой восстановления, ранбуки, проверки из ресерча, нагрузочный тест, письменный ответ Selectel про UDP, подпись образов и SBOM, панель трафика.
- **8. Первая живая игра.** Накануне — `just preflight`. Судье заранее выдаётся ссылка на запасной Телемост. Критерии успеха записываются до игры: ни одной утечки звука между комнатами, никто не ушёл в Телемост. После — короткий опрос, разбор журнала и телеметрии, правки.

Дальше — бэклог из раздела спеки «Не в MVP»: запись, аккаунты, роли и приватность, баллот, автоотсчёт POI по журналу, чаты подкомнат.

### Решения автора, принятые сознательно

- Код ссылки и id раунда — одно и то же: утёкшую ссылку не перевыпустить, её раунд удаляет администратор. Разделить можно позже миграцией.
- Ссылки организатора нет; контроль — служебные команды администратора на сервере.
- Формальности по персональным данным (политика, согласие, сроки хранения) на этом этапе не делаются. Имена и чат хранятся вместе с раундом; удалить их по просьбе можно служебными командами.
- Защита ветки и отдельный токен для Claude в GitHub не настраиваются; достаточно хука.
- Стенд арендуется после среза 6, а не вторым срезом; срезы 1–6 проверяются локально ([ADR 0001](adr/0001-stand-after-slice-6.md)).
