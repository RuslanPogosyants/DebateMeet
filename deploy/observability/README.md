# Клиентские метрики

Это конфигурация для среза С. Prometheus и Grafana сейчас не развёрнуты. Бэкенд отдаёт `/metrics` только loopback-клиенту; публичный Caddy возвращает для этого пути 404. Будущий collector должен работать в той же host-сети, а доступ к его данным настраивается при подготовке стенда.

`prometheus.yml` подключает правила из `client-recording-rules.yml`. `client-dashboard.json` — импортируемая Classic JSON-модель Grafana; при импорте выберите свой Prometheus datasource. Применение конфигурации и проверка на настоящем сервере входят в срез С.

Исходные серии `debatemeet_client_window_28d_*` — **gauges скользящего окна**, сообщённые клиентами. Старый день удаляется, поэтому значения могут уменьшаться. Правила используют текущие значения и отношения; `rate`, `increase` и повторное суммирование по времени для них не применяются. Пустое окно остаётся без данных; оно не подставляется как успешный ноль.

Показатели первого звука — `decoded_playback_proxy`: рост энергии декодированного входящего аудио при разрешённом тракте воспроизведения. Это не физическая слышимость. Рядом показываются доля наблюдаемых измерений и покрытие качества. Сон, пропуски, заблокированный звук, пустая комната и отсутствующая статистика не превращаются в хорошие участнико-минуты.

Верхняя конечная граница histogram bucket — 10 секунд. Поэтому правила целей используют точные доли измерений в соответствующем bucket, а не p95, который мог бы оказаться ограничен этой границей. Пороговые доли и покрытие нужно оценивать вместе; локальный прогон не доказывает 28-дневный SLO.

Эксплуатационные alerts, маршруты уведомлений и пороги реального объёма настраиваются в срезе С после появления сервера и данных. Идентификаторы раундов, участников, сессий и версии клиента в метках отсутствуют.

Формат: [модель dashboard Grafana](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/view-dashboard-json-model/), [типы метрик Prometheus](https://prometheus.io/docs/concepts/metric_types/).
